# spec-audit 0.5 (phase 1) on a pilot project: eval results

**Setup:**
- Same scope as the v2 eval (Workflows + Templates), baseline `0f7f4d3f99`, same traits and owner scope filters.
- **Rule packs:** the v2 packs (old KB). The authority cap and the new domains are *not* in this eval, so any change is attributable to phase 1:
  - entity cards (`references/web-patterns.md`);
  - invariants;
  - buckets;
  - suppressed;
  - depth `standard`.
- **Critical flows (eval assumption, not confirmed by the owner):** create/configure a workflow; run a workflow and see the result.
- **Runs:** two independent runs, `v3a` and `v3b`. Each run has two cluster agents and one triage agent.
- **Judge:** an impartial agent mapped each action list to the rubric (`docs/superpowers/notes/evals/pilot-rubric.json`). `skills/spec-audit/scripts/score.py` aggregated the counts.

**Deviation from the protocol.** Triage (Phase 5–6) ran in a subagent, not in the main session. The skill says triage is never delegated. Two of the three false claims below survived this delegated triage.

**Verdict: phase 1 does not pass.** It does not make the auditor better overall. It moves recall:
- **What it fixed:** the pattern class it was built for. G2 and G4 are now found in both runs. G5 and G6 are routed as BUGs, no longer as product questions.
- **What it lost:** spec-specific UI details that no pattern covers. G10, G12, G17 and G18 passed in v2 and fail in both v3 runs.

## What phase 1 found that the rubric does not credit

Both runs found several real defects outside the rubric. The judge or triage verified them in the code.
- **Concurrent runs** (both runs): "Confirm run" stays clickable while the start request is pending, and the backend allows parallel individual runs. Stop then cancels only the first run.
- **Template delete double submit** (v3a): the confirm button's `loading` is visual only, so a second click sends a second DELETE.
- **"Cancel run" without confirmation** (v3b): in the run progress modal, "Cancel run" stops the run with no confirmation, unlike the header Stop. Stop failures are silent.
- **Output picker race** (v3b): the picker saves immediately, and Confirm is not blocked while that save is in flight.
- **Raw UUIDs on a deleted template** (both runs): a template 404 shows two raw UUIDs, the retry can never succeed, and the stale row stays in the list.
- **Stale-data swap** (both runs): the workflow page and activity logs replace already-loaded data with the error stub after one failed refetch.

The rubric was built from the v1 run's reviewed findings. It rewards finding *those* items and has no way to credit new true positives. A fair comparison needs either a seeded-defect fixture or an owner review of the new findings.

## Diagnosis

1. **Pattern tunnel vision.** The entity cards absorbed the agents' attention. Spec-walk details with no matching pattern dropped out entirely: the Cancel semantics in the run modal, input = output confirmation on submit, the wrong template kind in the URL, discard on × or backdrop. They are not even Highlights. The lenses run the cards *first* and give no explicit instruction to walk every control and step the spec names.
2. **False "covered" through mocks.**
   - A unit test that mocks the very function deciding the behaviour (`getDefaultWorkflowTab`) was counted as covering it.
   - A service test with a mocked repository was counted as proving query scoping.
   - Lens 2b says "an assertion on the distinguishing condition" but says nothing about mocks of the logic under test.
3. **Questions bucket ambiguity.** v3a put questions into Must/Should; v3b put them into Highlight. `actions-schema.md` does not say how a `question` is bucketed, so the question share and the caps are not comparable between runs.
4. **Agreement at 80%.** Most of the disagreements are WEB-008 and WEB-010 on entities touched by the role filter (OK vs DECISION vs GAP). Verdict guidance for "partly suppressed by a filter" is missing.
5. **Must overflow is real, not noise.** Of 12–14 Must items, 11–12 are confirmed BUGs. The cap warning works as intended: it tells the owner to split the scope (templates and workflows separately).

## Proposed fixes (not applied; owner decision per plan Task 5 step 4)

- **Lenses §1:** after the entity cards, add a mandatory **spec walk**. Every control, step and state named in the spec gets one line: defined, tested, or gap. Uncovered items go to Highlight at minimum. This targets G10, G12, G17 and G18.
- **Lenses §2b:** add a rule. A test that mocks the function or repository that *decides* the behaviour does not cover that behaviour. Name the mock in the evidence. This targets G9 and G15.
- **`actions-schema.md`:** `question` items get `bucket: "question"`. They are counted separately and never against the Must/Should caps.
- **`web-patterns.md`:** a cell whose behaviour is fully removed by a scope filter gets the verdict `DECISION` with the filter cited. A cell partly removed is judged on the remaining behaviour.
- **Triage must stay in the main session.** Delegating it let two false claims through.
- **Measure the effect** with a re-run (about 1.5M tokens for two runs, including triage). Better: build the seeded-defect fixture from the colloquium (phase 2), so new true positives count.
