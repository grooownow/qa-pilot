# Независимое ревью книги «Качество решает всё» как источника для qa-pilot

Дата: 2026-10-19. Ревьюер: независимый агент (позиция senior QA и специалиста по теории тестирования).
Предмет: книга (819 стр., ручное тестирование) и построенный по ней свод `knowledge/catalog/rules/` (1137 записей).
Ссылки вида `s1-c09-03 / с. 72–78`: `chunk_id` и печатные страницы (`printed_pages`) из метаданных кусков.

## TL;DR

- **Сильная практическая книга для джуна, слабая теоретическая база.** Чек-листы по формам, API (BINMEN/POISED), мобильным прерываниям, локализации, WCAG 2.2, HIG и Material написаны на живых кейсах, актуальны на 2026 год и местами выдающиеся для русскоязычной литературы. Теория (принципы, тест-дизайн, уровни, подходы) упрощена до набора тезисов для собеседования. Часть тезисов неверна или выдаёт мнение автора за отраслевой стандарт.
- **Найдено 48 расхождений (4 высоких, 24 средних, 20 низких) с ISTQB v4, ISO/IEC 25010/29119/29148, RFC и первоисточниками.** Самые важные для qa-pilot: тест-дизайн подаётся как «математика без риска пропуска бага»; 2BVA объявлен «устаревшим»; ошибочные «проценты покрытия багов» у pairwise и 3-wise; игнорирование `Accept` объявлено багом (по RFC 9110 сервер вправе так делать); JWT назван «зашифрованным»; миф «56% багов из требований» и кривая стоимости 1–10–100 подаются как статистика; неверно описаны туры Уиттакера; неточности про ACID, BASE и MongoDB.
- **Крупные пробелы:** безопасность (сознательно пропущена, OWASP не упомянут ни разу), автоматизация и архитектура тестов, нестабильные (flaky) тесты, контрактное тестирование, наблюдаемость и тестирование в проде, риск-ориентированное тестирование, сессионное исследовательское тестирование (SBTM) и эвристики context-driven школы, тестирование самих ИИ/LLM-систем (глава про ИИ — только про ИИ как инструмент ручного QA), приватность данных.
- **Оценки по аудиториям:** новичок 7, junior manual QA 8, middle/senior 5, автоматизатор 3, тест-лид или менеджер 3, разработчики и PM 4 из 10.
- **Как источник детерминированных правил для qa-pilot: 6/10.** Хорош для проверок живого продукта (a11y, формы, l10n, мобильные) и формы артефактов. Опасен там, где авторская догма превращена в `must`/`should`-правило со статусом `verification: ok`. Статус `ok` сейчас означает «точный пересказ книги», а не «верно по стандарту». Конкретные ложноположительные правила уже есть: QAC-API-085, QAC-TD-008, QAC-FORM-004.
- **Рекомендация.** Добавить над сводом нормативный слой из открытых источников: OWASP ASVS 5.0 / API Top 10, W3C ACT Rules, RFC 9110/9457, Zalando API Guidelines, GOV.UK Design System, NIST SP 800-63B-4, правила качества тестового кода из документации Playwright и ESLint-плагинов. Затем пройти по 234 детерминированным правилам с внешней сверкой и ввести поле `authority`.

## 2. Сильные стороны

1. **Практичность и конкретика.** Почти каждая техника показана на реальном сайте с реальной находкой. Например, в API-главе на публичной песочнице `automationintesting.online` найдены: список чужих броней без авторизации, подделка `depositpaid: true` (по сути mass assignment / OWASP API3:2023), падение `null → 500` (s2-c05-03, с. 178–184). Это лучший способ учить, и такие находки легко превращаются в правила.
2. **Актуальность на 2026 год:**
   - WCAG 2.2 с новыми критериями (2.4.11, 2.5.8 против 2.5.5, без устаревшего 4.1.1);
   - INP вместо FID с марта 2024, верные пороги CWV (s7-c04-02, с. 722–724);
   - классификация тестов нагрузки совпадает с документацией Grafana k6 (s4-c07-02);
   - метод QUERY: книга упомянула его раньше, чем вышел RFC 10008 (июнь 2026).
3. **Доменные чек-листы, которых нет в классике:**
   - мобильные прерывания и OEM-«убийцы» фоновых процессов, Huawei без GMS, GPS, который отключается при заряде ниже 15% (s6-c02-02, с. 503–505);
   - календари, форматы и первые дни недели для локализации (s4-c05-01);
   - тёмные паттерны и 18 законов UX как дефекты;
   - severity в геймдеве;
   - каталог «любимых грабель» для error guessing: двойной клик, кнопка «Назад», протухшая сессия, ZWSP, `utf8mb4` (s1-c09-08, s1-c07-02).
4. **Артефакты описаны хорошо (s1-c04…c06).** Баг-репорт (ЧГК-заголовок, воспроизводимость, workaround, 1 баг = 1 тикет, нейтральный тон) почти совпадает с ISTQB v4 §5.5. Пример отчёта с явным go/no-go — хороший образец для детерминированных проверок.
5. **Честность автора о границах своей экспертизы:** безопасность, Unity/UE, cause-effect graph («ни разу не рисовал»), тест-план («писал дважды за 5 лет»). Это редкость, и это помогает понять, где книге нельзя доверять.
6. **Русскоязычный контекст:** GDPR и PSD2 в требованиях, кейсы Kufar/Onliner/AliExpress, белорусское и российское законодательство о доступности, русская терминология с английскими эквивалентами.
7. **Правила для ИИ-агента** (s7-c06, с. 783–784): не строить pairwise средствами LLM, следить за дрейфом контекста, перепроверять сгенерированное. Это прямо применимо к qa-pilot.

## 6. Пригодность как источника правил для qa-pilot

### 6.1. Где книга надёжна

- **Доступность** (133 правила). Привязка к критериям WCAG 2.2 с номерами SC — нормативный якорь. Риск невелик: ошибки исправляются сверкой с текстом SC.
- **Форма артефактов** (test-artifacts, 26 детерминированных). Баг-репорт, кейс и отчёт проверяются скриптом. Оговорка: такие проверки измеряют соответствие шаблону, а не качество тестирования (риск Гудхарта). Их стоит держать как `should`, а не `must`, кроме полей, без которых дефект нельзя воспроизвести.
- **Чек-листы живого продукта:** формы, мобильные устройства, l10n, тёмные паттерны, CWV. Это эвристики с высокой отдачей и низким риском ложного срабатывания, если формулировать их как «проверь X», а не «X — дефект».
- **Правила для ИИ-агента** (`ai-in-qa`): прямо полезны.

### 6.2. Где книга опасна для детерминированного аудита

- **Тест-дизайн:** QAC-TD-008 требует 3BVA и ставит находку на 2BVA, хотя ISTQB считает оба варианта допустимыми. Аудит тест-плана будет шуметь.
- **API:** QAC-API-085 (406) противоречит RFC 9110. Возможны и другие правила с опорой на «стандарт RESTful» или на «422 профессиональнее».
- **Формы:** QAC-FORM-004 (раздельные поля ФИО) конфликтует с QAC-L10N-014 и практикой W3C/GOV.UK.
- **Числовые пороги:** таблица Response Time, проценты покрытия pairwise, 80/20. Их нельзя использовать как критерии pass/fail.
- **Системный риск.** Ни у одной записи нет `verification: doubtful`. 850 записей помечены `ok`, 287 — `fixed`, `modern_note` есть у 43. Сверка проверяла верность пересказа книге, а не корректность по внешним стандартам. Поэтому авторские мнения и отраслевые нормы выглядят в своде одинаково авторитетно.

### 6.3. Чего не хватает для сценариев qa-pilot

| Сценарий qa-pilot | Покрытие книгой |
|---|---|
| Аудит требований и спецификаций | Частично: размытые слова, критерии качества, AC/Gherkin. Нет требований безопасности, приватности, NFR с перцентилями и SLO, трассируемости, анализа рисков |

## 8. Конкретные шаги для базы знаний

1. **Срочно исправить ложноположительные правила:**
   - **QAC-API-085:** перевести в `heuristic`. Формулировка: «политика content negotiation задокументирована: 406 или представление по умолчанию; оба варианта допустимы по RFC 9110 §12.5.1».
   - **QAC-TD-008:** заменить на «для каждого стыка есть 2-value BVA; для высокого риска или порогов вида `>= N` — 3-value», со ссылкой на ISTQB.
   - **QAC-FORM-004:** добавить `decision`: допускается одно поле «Полное имя»; правило не применяется к именам; согласовать с QAC-L10N-014.
2. **Ввести поле `authority`** со значениями `normative` (RFC/W3C/ISO/NIST), `vendor-guideline` (HIG/Material/Google), `industry-practice` (ISTQB/OWASP) и `author-opinion`. Детерминированный аудит выдаёт `must` только при `normative` или `industry-practice`. Отдельно ввести статус `external_check` (`aligned` / `conflict` / `n/a`), независимый от `verification`.
3. **Пройти внешней сверкой 234 детерминированных правила** (там самый высокий риск ложных срабатываний), затем `must`-правила тем test-design, api, forms, databases, performance. Чек-лист сверки: таблица в разделе 3 этого отчёта.
4. **Удалить или пометить как ненормативные числовые утверждения книги:** 56% / 1–10–100, проценты покрытия pairwise и 3-wise, «отраслевые» пороги Response Time, 80/20. Использовать их только как пример, но не как критерий.
5. **Добавить недостающие правила, которые прямо следуют из теории:**
   - атрибут трассируемости в тест-кейсе;
   - раздел продуктовых рисков в тест-плане;
   - критерии покрытия state transition (с недопустимыми переходами);
   - один невалидный параметр на негативный тест (в книге есть — проверить, что попал в свод);
   - перцентили и SLO в NFR;
   - CWV по 75-му перцентилю полевых данных.
6. **Новые домены из P0/P1-источников:** `security` (ASVS 5.0 + API Top 10, с маппингом существующих QAC-API-088/089/128), `test-code-quality` (Playwright/ESLint/test smells), `ai-systems` (OWASP LLM Top 10 + NIST AI 600-1), `auth` (NIST 800-63B-4). Для каждого начинать со стабильных ID из первоисточника. Это упростит повторную сверку при выходе новых версий.
7. **В `summary.md` честно отразить:** «verification = верность пересказу; корректность по стандартам проверена только для N правил». Добавить раздел «Известные расхождения книги со стандартами» со ссылкой на этот отчёт.
8. **Для `ai-in-qa`** добавить правило о конфиденциальности (не отправлять NDA-код и продакшн-данные во внешние LLM без разрешения политики) и правило об оракуле (требования, выведенные из diff, не могут быть единственным оракулом для этого же diff).
