# Пилот: аудит требований и тест-плана по своду Суркова на pawfile (2026-10-12)

Это вход для спецификации подпроекта C (скилл аудита). Отчёт по самому pawfile лежит в pawfile: `docs/qa/2026-10-12-surkov-spec-audit.md`, не закоммичен.

## Что сделали

**Охват:** 33 документа pawfile — 13 спецификаций фич, 10 спецификаций страниц, states, 00/01/02 и testing-strategy.

**Правила:** 616 правил свода с `applies_to` = requirements/test-plan, без игр, iOS/Android-гайдлайнов и десктопной инсталляции. Правила упакованы в 5 компактных пакетов, по строке на правило, всего около 70 тыс. токенов. Каждый агент получал все пакеты.

**Процесс:**
1. Детерминированный проход: регулярка SRK-REQ-014.
2. 5 агентов по группам спецификаций. Каждый сначала читал решения проекта и только потом применял правила.
3. Сведение отчёта и перепроверка всех P1 по коду.

**Итог:** P1 — 4 находки (3 причины), P2 — 95, P3 — 70, недостающих сценариев — 140. Все P1 подтвердились при перепроверке.

## Главные уроки для скилла

1. **Аудит одних спецификаций не работает, обязательна сверка с кодом.** Около трети кандидатов в «недостающие сценарии» уже покрыты тестами, и без grep по `*.test.*`/`*.spec.ts` отчёт превращается в шум. Все P1 и лучшие P2 найдены сравнением «спецификация утверждает X» с кодом: action, миграцией, телом RPC, mock'ом в тесте. Скилл должен иметь колонку «spec ↔ code» с file:line реализации для каждой P1/P2.
2. **Самые ценные правила** — модели состояний и переходов и недопустимые события (TD-039/040/042), таблицы решений (TD-030/031) и противоречия (REQ-009). Скилл должен **обязательно** строить таблицу «действие × состояние» для каждой сущности с жизненным циклом (ссылки, задания извлечения, удаление, soft-delete) и сверять каждый переход с тем, кто его записывает в коде.
3. **Инвариант во всех путях записи.** Повторяющийся класс дефектов: правило проверяется в одном пути (review, extraction) и пропущено в другом (ручной ввод). Нужен отдельный шаг: для каждого инварианта перечислить все пути записи.
4. **Противоречия между документами** дают больше всего находок. Нужно сравнивать каждую спецификацию с соседними (feature ↔ page), с `docs/decisions/*` и между её собственными разделами «Изменения YYYY-MM-DD» и блоком AC. Проверки «X в коде нет / есть» дешёвые и результативные.
5. **Детерминированная регулярка размытых слов (REQ-014) почти вся шумит:** 15 из 16 совпадений ложные. Слова стояли в обоснованиях, открытых вопросах и UI-копирайте («удобно»), а не в требованиях. Что нужно:
   - пропускать цитаты «…», код, разделы rationale, history и open questions;
   - расширить словарь на уровне проекта: «корректно», «корректный» пропущены;
   - проверять только строки AC и требований.
6. **Анти-false-green — отдельный проход по тестам.** Mock, жёстко зашивающий success у guard'а (rate-limit удаления), — это P1. Для каждого security-AC найти тест, который проверяет конкретный код отказа, и убедиться, что mock не фиксирует успех.
7. **Нефункциональные проверки — один раз на проект, а не на каждую спецификацию.** Уровень WCAG, браузеры и устройства, CWV, офлайн PWA, `playwright.config` projects, smoke/regression-гейт: CI-триггер, DoD.
8. **Фильтрация правил по профилю проекта.** Для Server-Action PWA шумят:
   - REST-статусы (API-014/018/022/024/039…);
   - тёмные паттерны цен и подписок (UXL-023…036), если нет денег;
   - валюты, адреса, телефоны и RTL в L10N;
   - нативные мобильные правила (батарея, звонки, FaceID, process death);
   - формальные атрибуты тест-кейсов (ART-004/009), если проект осознанно пишет AC списком;
   - сложность паролей (FORM-030/031).

   Правила нужно пред-фильтровать по профилю: web PWA или native, есть ли деньги, адреса, REST.
9. **Калибровка серьёзности.** `must` в книге — это не P1. P1 только при реальном дефекте, утечке данных или безопасности либо отсутствии регресс-гейта. Дрейф документации — P2 или P3. a11y SC при free-beta — P2.

## Пробелы каталога (правил нет, а находки реальные)

- Поведение при деградации инфраструктуры: fail-open или fail-closed у rate-limiter, внешних зависимостей, проверок.
- Остаточное окно после отзыва сессии при локальной проверке JWT.
- Парные guard'ы (per-IP + per-email) должны быть доказаны каждый по отдельности: тест, где оба бакета «упали», не доказывает ни один.
- Часовой пояс «сегодня» для валидации дат и сроков (частично REQ-010).
- Утечка внутренних идентификаторов (UUID владельца в путях хранилища) через публичные эндпоинты: тело RPC против заявлений спецификации «PII не покидает сервер».

Добавлять их как собственные правила проекта qa-pilot (не из книги, с отдельным префиксом, например `QAP-`), решим в спецификации C.

## Предложение для спецификации C (черновой каркас)

- **Вход:** набор документов требований и тест-плана, профиль проекта (`docs/qa/project-profile.md`), решения проекта.
- **Фазы:**
  1. Профиль, фильтр правил и детерминированные проверки.
  2. По каждой спецификации: модели состояний, таблицы решений, BVA, противоречия.
  3. Сверка с кодом и тестами (covered, gap, drift).
  4. Проход по анти-false-green.
  5. Нефункциональные проверки на уровне проекта.
  6. Сведение и калибровка P1/P2/P3.
- **Выход:** отчёт в формате пилота: итог, P1, топ-P2, сквозные выводы, решения владельца, полные находки.
