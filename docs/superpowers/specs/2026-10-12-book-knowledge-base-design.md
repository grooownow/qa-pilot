# База знаний по книге «Качество решает всё» (подпроекты A + B) — дизайн

Дата: 2026-10-12 · Ветка: `feat/book-knowledge-base` · Статус: на ревью

## 1. Цель

Превратить книгу «Качество решает всё: полное руководство по
тестированию ПО» (819 стр., PDF) в:

- **справочник**, с которым агенту удобно работать (быстро найти нужную главу или
  раздел по теме и прочитать только её);
- **свод знаний**: жёсткие правила, рекомендации и практические советы, каждый со
  ссылкой на источник и пометкой, можно ли проверить его автоматически;
- **краткое содержание** для пользователя: о чём книга и чем она полезна qa-pilot.

Это фундамент для следующих подпроектов, у которых будет своя спецификация:

- **C** — скилл аудита по своду знаний. Пять целей: требования, тест-планы
  qa-pilot, код автотестов, живой продукт, внешние тест-кейсы.
- **D** — встраивание в `plan-tests`, `cover`, `audit`.

Дизайн A+B заранее учитывает потребности C/D: у каждого правила есть поля
`applies_to` и `check`.

## 2. Ограничения

- **Авторское право.** Полный текст книги не попадает в git: репозиторий публичный,
  лицензия MIT. В git идут только наши пересказы (правила, чек-листы, саммари),
  оглавление без текста и метаданные. Сырой текст собирается локально скриптом
  в папку из `.gitignore`.
- **Без векторной базы и серверов.** Агент ищет через индекс тем, grep и Read.
  JSONL нужен для машинной обработки и возможного RAG в будущем.
- **Без новых зависимостей.** Скрипты на Python (только стандартная библиотека)
  плюс `pdftotext` из poppler.
- **Книга о ручном тестировании.** Автоматизации в ней нет. Ценность для нас
  в том, *что* проверять, а не *как писать* автотесты.

## 3. Структура файлов

```
knowledge/catalog/
  README.md            # что это, как пересобрать, как агенту искать, лицензионная оговорка
  summary.md           # краткое содержание для человека (RU)
  toc.json / toc.md    # оглавление: раздел → глава → подраздел, страницы, chunk_id, кол-во слов (без текста)
  topics.md            # индекс тем: тема → chunk_id → файлы правил/чек-листов
  rules/
    <topic>.json       # источник истины: правила/рекомендации/советы/пункты чек-листов
    <topic>.md         # генерируется из json — для чтения человеком и агентом
  raw/                 # .gitignore — только локально
    pages/NNN.txt      # текст постранично (pdftotext)
    chunks/<chunk_id>.md   # смысловые куски с front matter
    chunks.jsonl       # те же куски одной строкой каждый
scripts/kb/
  build_chunks.py      # PDF → raw/pages → raw/chunks + toc.json/toc.md
  render_rules.py      # rules/*.json → rules/*.md, + проверка схемы
```

`raw/` добавляется в `.gitignore`. Без `raw/` плагин продолжает работать
по правилам и саммари, с `raw/` агент может открыть полный исходный фрагмент.

## 4. Подпроект A — нарезка

**Источник.** `pdftotext` постранично. Из каждой страницы удаляются колонтитулы
(повторяющаяся шапка «ГЛАВА N: …» и номер страницы внизу). Сохраняются оба номера:
`pdf_page` (индекс в PDF) и `printed_page` (напечатанный номер, примерно на 2
меньше). Картинки (скриншоты) не извлекаются, в куске ставится пометка
`[рисунок]`. Это осознанное ограничение.

**Границы кусков.** Берутся из оглавления: 7 разделов, ~60 глав, ~370 подразделов.
Заголовки подразделов ищутся в тексте по порядку. Один кусок = один подраздел.
Если подраздел длиннее ~1500 слов, он делится по абзацам на части `…-p1`, `…-p2`.
Короткие (<80 слов) сливаются со следующим подразделом.

**chunk_id.** `s{раздел}-c{глава:02}-{подраздел:02}[-pN]`, например `s1-c09-02`
(граничные значения).

**Front matter куска:**
```yaml
id: s1-c09-02
section: "Раздел 1 — Теория тестирования"
chapter: "Глава 9: Техники тест-дизайна"
heading: "2. Анализ граничных значений (BVA)"
pdf_pages: [68, 74]
printed_pages: [66, 72]
words: 1240
topics: [test-design, bva]
```
`topics` проставляются по словарю тем из `topics.md` (теги назначаются
вручную или агентом на этапе B, скрипт их переносит).

**Детерминированность.** Повторный запуск даёт побайтно одинаковый результат.

**Проверки A (критерии готовности):**
- каждая запись оглавления сопоставлена с куском, несопоставленные выводятся в отчёт;
- суммарный текст кусков покрывает ≥98% очищенного текста книги;
- два запуска подряд → `diff` пустой;
- `git status` не показывает файлов из `raw/`.

## 5. Подпроект B — свод знаний

### 5.1 Схема записи (`rules/<topic>.json`, массив)

```json
{
  "id": "QAC-FORM-012",
  "kind": "rule | recommendation | tip | checklist",
  "severity": "must | should | nice",
  "title": "Короткая формулировка",
  "statement": "Что именно требуется / рекомендуется, своими словами",
  "rationale": "Почему (по книге)",
  "applies_to": ["requirements", "test-plan", "test-code", "live-product", "test-cases"],
  "check": {
    "mode": "deterministic | heuristic | manual",
    "how": "Как проверить: что искать, на каком артефакте, критерий pass/fail"
  },
  "modern_note": "опционально: актуальность сейчас, расхождение с современными практиками",
  "source": { "chunk_id": "s1-c07-02", "printed_pages": [43, 44] },
  "tags": ["forms", "validation"]
}
```

- `kind`: `rule` — жёсткое требование автора; `recommendation` — «лучше делать так»;
  `tip` — практический совет; `checklist` — пункт тематического чек-листа.
- `check.mode`:
  - `deterministic` — проверяется скриптом или поиском, например «в требовании
    нет слов-мусора», «у тест-кейса есть ожидаемый результат», «контраст ≥ 4.5:1
    через axe»;
  - `heuristic` — нужно суждение агента;
  - `manual` — только человек.
- `statement` — всегда пересказ. Дословные цитаты запрещены (кроме терминов и
  коротких формулировок стандартов, например критериев WCAG).

`render_rules.py` проверяет схему: уникальные id, допустимые значения enum,
непустые обязательные поля. Если `raw/` есть, дополнительно проверяет, что
`chunk_id` существует и страницы попадают в его диапазон. Затем генерирует `.md`.

### 5.3 Глубина извлечения (весь охват, без молчаливых сокращений)

- **Глубоко** — правила, чек-листы и советы максимально полно: раздел 1
  целиком, 2.5 (тестирование API), 4.1–4.7, 5.1–5.6, 6.1–6.5, 7.4, 7.6.
- **Средне** — в основном советы и «на что смотреть», инструкции по
  инструментам кратко: 2.1–2.4, 2.6–2.11 (DevTools, Postman, Swagger,
  GraphQL, Proxyman), 3.x (SQL и БД), 6.6–6.10 (Xcode, Android Studio,
  жизненный цикл), 7.1–7.3, 7.5, 7.7 (продуктивность).
- **Только оглавление и саммари** — 5.7 (доступность в Беларуси),
  7.8 (карьера, резюме, собеседования), «Об авторе». Правила из них не
  извлекаются, потому что для аудита продукта они нерелевантны. В саммари
  они упоминаются одной строкой.

### 5.4 Процесс извлечения

1. **Разметка тем.** Один агент проходит `toc.json` и назначает `topics`
   каждому куску. Результат записывается в `topics.md`.
2. **Извлечение.** Параллельные агенты, по одному на тему или группу тем
   (≈10 агентов). Каждый читает только свои куски и **дописывает записи
   в `rules/<topic>.json` по мере работы** (правило из глобального CLAUDE.md).
   Если агент упрётся в лимит сессии, сделанное не потеряется.
   Рабочие заметки агентов пишутся в scratchpad.
3. **Верификация.** Отдельный агент на каждую тему сверяет каждую запись
   с исходным куском:
   - есть ли это в книге;
   - не искажён ли смысл;
   - верны ли `severity` и `check.mode`;
   - нет ли дословного копирования.

   Ложные записи удаляются, сомнительные помечаются. Отчёт пишется
   в scratchpad.
4. **Дедупликация между темами.** Общие правила (например, про баг-репорт
   в разных главах) сводятся в одну запись. В остальных местах вместо
   дублей ставятся ссылки через `tags`.
5. **Рендер и валидация.** `render_rules.py` должен пройти без ошибок.
6. **Саммари** (`summary.md`, RU, ~1–2 стр.):
   - о чём книга и кто автор;
   - карта разделов;
   - что особенно ценно для qa-pilot и как будем использовать;
   - что устарело, спорно или вне скоупа (автоматизация, глубокая безопасность);
   - топ-15 жёстких правил.

### 5.5 Критерии готовности B

- Для каждой главы из уровней «глубоко» и «средне» есть хотя бы одна запись
  или явная пометка в `topics.md`, почему записей нет.
- Валидатор проходит, id уникальны.
- Верификация выполнена для 100% записей уровня «глубоко» и выборочно
  (≥30%) для уровня «средне». Доля удалённых записей указана в отчёте.
- Статистика в `knowledge/catalog/README.md`: сколько записей по `kind`,
  `severity`, `check.mode` и по темам.
- `summary.md` написан.

## 6. Использование агентом (контракт для C/D)

1. Найти тему в `topics.md`, оттуда получить файл правил и `chunk_id`.
2. Прочитать `rules/<topic>.md` или отфильтровать `rules/<topic>.json` по
   `applies_to`, `check.mode`, `severity`.
3. Если нужна первоисточная деталь и `raw/` есть — прочитать
   `raw/chunks/<chunk_id>.md`. Если `raw/` нет — сослаться на
   печатную страницу.

## 7. Вне скоупа A+B

- Скилл аудита (C) и изменения существующих скиллов (D).
- Распознавание текста на скриншотах (OCR).
- Перевод свода на английский. Язык записей — **русский**: это
  язык источника и язык пользователя. Если плагин станет многоязычным,
  перевод можно сделать отдельной задачей, схема это позволяет (`title_en`).

## 8. Риски

- **Нестабильное сопоставление заголовков** (вёрстка Google Docs, спецсимволы
  `​`). Нормализуем пробелы и невидимые символы, сравниваем по нормализованной
  строке и печатной странице. Несопоставленные заголовки идут в отчёт,
  а не пропускаются молча.
- **Галлюцинации при извлечении.** Обязательная ссылка на `chunk_id`
  и отдельный проход верификации.
- **Объём.** ~1,6 МБ текста (~450k токенов). Извлечение идёт параллельно
  по темам, результаты сохраняются по ходу работы.
