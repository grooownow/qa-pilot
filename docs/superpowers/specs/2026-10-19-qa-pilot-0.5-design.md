Date: 2026-10-19. Status: draft for owner approval.

Inputs:
- `docs/superpowers/notes/2026-10-19-spec-audit-colloquium.md`: a four-agent colloquium on closing spec-audit's weaknesses.
- `docs/superpowers/notes/2026-10-19-book-independent-review.md`: an independent review of the source book and the rules catalog built from it.

## 1. Intent and why

**Owner's doubt.** In daily work an AI-driven development loop writes and runs tests several times per task. Yet the owner has strong doubts that anyone checks the *completeness and correctness* of those tests.

**Small tasks shrink testing to spot checks.** Nobody re-reads the whole picture, so a change that ripples into other parts of the system goes unnoticed.

**The motivating miss.** An entity is modified while it is being deleted. The case was unhandled, the user saw no clear error, and the audit did not surface it.

The owner wants qa-pilot to own the QA part of work in two scenarios.

**Scenario 1: project audit.** Runs when:
- the owner enters a new project whose "test framework" is partial (harness, libraries, layers, CI);
- an intermediate audit of a live project is due;
- a large feature, or a round of small changes, has finished and the whole picture needs re-checking.

**Scenario 2: the task QA step, every day, in every task.** It is embedded in a development orchestrator such as a pilot project's feature workflow skill.
- **At planning:**
  - check the acceptance criteria against the task logic and the existing system;
  - map which higher-level components the change touches;
  - decide which tests to change or add.
- **After implementation:**
  - check that the tests really cover the change;
  - find where the point change affects the rest of the system;
  - ask "is this intended?" when that is unclear;
  - pin each intended new behaviour with a test.

**What a good result looks like (owner's words):** an impact analysis. Where does this change reach? What there is expected, and what is questionable? Which tests now pin the expected behaviour?

**The knowledge base must be correct and complete enough for web projects.** The book review found 48 discrepancies with standards and three rules that produce false positives. It also found the book blind to security, test-code quality, contract testing, risk-based testing and AI systems. The owner has no other books. Agents write our own rules from open, authoritative sources.

## 2. Goals, non-goals, anti-goals

### Goals
1. **The task QA step** (scenario 2): cheap enough to run on every task, with `plan` and `verify` modes and a stable contract for orchestrators.
2. **The project audit** (scenario 1): framework maturity, critical flows, then spec-audit per critical flow and a roadmap.
3. **Spec-audit phase 1** from the colloquium:
   - entity cards × web patterns, with a gate on empty cells;
   - web invariants as the source of expected results;
   - Must / Should / Highlight buckets with caps;
   - a "Suppressed by your filters" section;
   - critical flows recorded in the profile;
   - a machine-readable `-actions.json`;
   - `score.py`.
4. **Knowledge-base correctness:**
   - fix the three false-positive rules;
   - add `authority` and `external_check` fields;
   - an external check of the 234 deterministic book rules;
   - flag the numeric myths;
   - be honest about this in `summary.md`.
5. **Own knowledge base:** rule domains written by agents from open sources, each rule paraphrased, sourced and verified against its source.
   - `web-patterns` and `web-invariants`;
   - `security` (ASVS 5.0 / API Top 10);
   - `test-code` (Playwright / ESLint plugins / test smells);
   - `api-http` (RFC 9110/9457, Zalando);
   - `auth` (NIST 800-63B-4);
   - `test-strategy` (ISTQB v4 risk-based and coverage criteria, exploratory/SBTM, contract testing, testing in production);
   - `ai-systems` (OWASP LLM Top 10).

### Non-goals
- Running the product. That stays with `qa-pilot:test`.
- Merging or pushing anything without the owner.
- Editing the pilot project's repo. We ship an integration snippet; the owner adds it.
- The full ledger and a `delta` mode for spec-audit, the stack-specific code scanner, and the planted-bug fixture app. These are colloquium phase 2 and wait for phase-1 data.

### Anti-goals (would make this a failure even if it works)
- **Over-testing.** Volume that "sinks the boat": hundreds of scenarios, every corner case turned into a test, owner fatigue.
- **Dropping critical patterns to save volume.** The concurrent modify-vs-delete miss must not recur.
- **The task step costing like spec-audit.** If it costs about 500k per task, nobody runs it daily.
- **Wrong findings becoming wrong tests in the loop.** An invented expected result is pinned by a test; this is the precedent of finding #8 on a pilot project.
- **The knowledge base presenting author opinion as a standard.**
- **Copyrighted text in git.** The repo is public MIT, so rules are paraphrased with a source reference.

## 3. Constraints

- **Repo and branch.** The repo is public and MIT-licensed. Work continues on `feat/book-knowledge-base`, which is unpushed (owner to confirm). Commits are local; push and PR only on the owner's request.
- **Rules format.** The existing JSON schema (`knowledge/catalog/README.md`) plus the new fields. Our own rules go under `knowledge/qa-pilot/rules/<domain>.json` with `source.origin` (URL + section). Rules are written in Russian, like the existing catalog. Render and validate with `scripts/kb/render_rules.py`. The pack builder is `skills/spec-audit/scripts/rules_pack.py`.
- **Gates.** Tests for the scripts (`pytest` in `skills/spec-audit/scripts` and `scripts/kb`) must be green before completion.
- **Cost.** The owner is on a Pro-class budget. Each step states its token cost up front.

## 5. Components

### 5.1 Shared core: web patterns and invariants (new)
- **`knowledge/qa-pilot/rules/web-patterns.json` (`QAP-WEB-NNN`).** About 18 patterns: 10 marked `must-check`, the rest `highlight`. Each has:
  - `trigger`: a cheap applicability signal, grep signatures per stack family (React/TanStack, generic REST backend);
  - the check;
  - default severity;
  - the test level;
  - `book_refs` to QAC rules;
  - `authority`.

  The 10 must-check patterns are chosen from the colloquium lists: stale or deleted entity on save (modify × delete), concurrent run/double submit, mutation without error handling, modal closing before its request settles, refetch failure after data shown, uniqueness conflict (409) surfaced, UI-only permission check vs API, nested resource id not checked against its parent, session expiry mid-action, mode/flag-dependent routes and tabs. The author agent may swap one with a written reason.
- **`knowledge/qa-pilot/rules/web-invariants.json` (`QAP-WINV-NNN`).** U1–U6, which are the source of expected results when the spec is silent. Examples: no success after failure; every write has a visible failure reaction; no raw ids or stack traces shown; loaded data survives a failed refetch; a destructive action names what it destroys; a retry is possible only when it can succeed.
- **`references/web-patterns.md`.** The working brief generated from both JSON files: the entity card template and the verdict set OK / BUG / GAP / N/A (with evidence) / DECISION.

### 5.2 spec-audit 0.5 (phase 1)
- **Phase 0:**
  - ask for **critical flows** and store them in the profile (`## Critical flows`);
  - ask for scope filters, as now.
- **Lenses.** A new step, "entity cards": each entity with a lifecycle gets a card of must-check patterns, and each cell needs a verdict. §2d cites the invariants as a valid expected-result source.
- **Phase 5 triage gate.** A report with empty cells, or N/A without evidence, is not ready.
- **Phase 6 output buckets:**
  - **Must**: no cap; the rows are I≥4 patterns, BUGs, and anything on a critical flow;
  - **Should**: ≤8;
  - **Highlight**: one line each.

  Two new sections: "Highlighted, not drilled" and "Suppressed by your filters". Plus `-actions.json` alongside `-actions.md`.
- **`depth`: `critical` / `standard` (default) / `thorough`.** Aligned with plan-tests' smoke / standard / thorough wording. `critical` runs only the entity cards and the contradiction lens on critical flows.
- **`scripts/score.py`.** Scores an `-actions.json` plus findings against a rubric JSON (the pilot-project rubric converted). It prints pass / partial / fail per check, the bucket counts and the product-decision share.

### 5.3 `qa-pilot:task-qa` (new, scenario 2)
- **Input.** A ticket (tracker MCP) or a description with AC, plus in `verify` the diff (`git diff <base>...HEAD`). It reads `docs/qa/project-profile.md`.
- **`plan` mode.** Target ≤80k tokens; a measured estimate is still to come.
  1. **AC check.** Each AC is testable, consistent with the code, the sibling specs and the decisions, and missing nothing obvious from the entity cards of the touched entities. Findings go out as questions or proposed AC edits.
  2. **Impact map.** Touched modules → their consumers: shared components, hooks, API clients, routes, backend endpoints and their other callers. Built by grep/LSP over the repo; each edge cites `file:line`.
  3. **Test delta.**
     - Existing tests that must change, because they assert the old contract.
     - New tests by bucket, using the plan-tests scenario format.
     - Patterns from the cards that apply.
  4. **Output.** `docs/qa/tasks/<ticket>.md` plus a compact block for the orchestrator or ticket.
- **`verify` mode.** Target ≤100k.
  1. Reconcile the diff with the plan: what was planned, what was done, what was not planned.
  2. Recompute the impact from the real diff. A behaviour change outside the plan becomes "intended?": a question with the evidence.
  3. Completeness, using the three proofs (test, distinguishing assertion, layer in CI) per planned scenario and per Must pattern.
  4. Write the missing tests via `write-tests` under D6.
  5. Output: an updated task file plus a PR-ready block (QA verification: covered / added / questions / highlighted).
- **Guardrails:**
  - no new test without a sourced expected result;
  - ≤5 auto tests per task;
  - at most one new e2e;
  - BUG fixes need the owner.

### 5.4 `qa-pilot:project-audit` (new, scenario 1)
1. **Profile.** Run `onboard` if the profile is missing. Onboard gains a **framework maturity** section: which layers exist, runners, CI gates, mocking strategy, test data, selectors convention, flaky handling, coverage tooling. Each is scored present / partial / missing against the `test-code` and `test-strategy` rules.
2. **Critical-flows inventory.** Proposed from routes, entities and docs; the owner confirms 3–7 flows.
3. **Spec-audit per confirmed flow at `depth: critical`.** Specs if present, otherwise the code-derived behaviour. Budget: ≤250k per flow; the owner picks the flows. Sequential; reuses the run's profile and digest.
4. **An `audit` sample of the test code** around the critical flows.
5. **Roadmap.** `docs/qa/project-audit/<date>.md`, in this order:
   1. framework fixes;
   2. Must tests per flow;
   3. questions;
   4. Highlight.

   Plus an executable action list in English.

### 5.5 Knowledge base
- **Fixes.**
  - QAC-API-085, QAC-TD-008 and QAC-FORM-004 are changed per review §8.1.
  - The numeric myths (review §8.4) are marked `authority: author-opinion` with a `modern_note`.
  - `summary.md` gets a "Known discrepancies with standards" section.
- **Schema.** `authority` and `external_check` are added to the validator in `scripts/kb/`.
  - Backfill all 1137 QAC rules by rule: WCAG SC reference → `normative`; HIG/Material → `vendor-guideline`; else `author-opinion`. Then manual or agent upgrades where the rule matches a standard.
  - `rules_pack.py` applies the D9 cap.
- **External check of the 234 deterministic QAC rules.** Batched agents compare each rule with its standard and set `external_check`. Conflicts get fixed or demoted.
- **New domains** (§2 goal 5). Each is authored by one agent with web research and then verified by a second agent that checks every rule against the cited source; unsupported rules are dropped.
  - Caps:

    | Domain | Rules |
    |---|---|
    | security | ≤40 |
    | test-code | ≤35 |
    | api-http | ≤25 |
    | test-strategy | ≤25 |
    | auth | ≤15 |
    | ai-systems | ≤15 |

  - Licenses: CC BY / CC BY-SA sources are paraphrased with attribution; copyrighted books are paraphrased only, never quoted at length.
  - Domains are tagged with `needs-*` traits so packs stay small.
- **`ai-in-qa` additions:** a confidentiality rule and the rule that a requirement derived from a diff cannot be its own oracle (review §8.8).

## 6. Measurement

- **The script tests pass.**
  - `score.py` against a hand-made fixture;
  - `rules_pack.py` with the authority cap;
  - the validator with the new fields.
- **Spec-audit phase 1: 2 runs on a pilot project** (Workflows + Templates), about 1M tokens. Run **only after the owner OKs the cost.** PASS if both runs meet every criterion:
  - ≥16/21, with G2 and G4 passing both times;
  - 0 false absence or "covered" claims;
  - G10, G11 and G14 intact;
  - ≤15 Must+Should items;
  - ≤5 product questions;
  - 0 empty cells;
  - cell agreement ≥85%;
  - ≤560k per run.
- **task-qa trial.** A read-only `plan` + `verify` on one recently merged ticket of the pilot project, comparing what it finds with what the merged tests cover. Cost is reported. The owner judges usefulness. Optional, with OK.
- **KB.** Each new domain's verifier report lists rules dropped as unsupported. The external-check report lists conflict counts.

## 8. Builder-check answers (my calls unless marked)

1. **Rubric matching in `score.py`.** The run never sees rubric ids, which keeps the eval blind.
   - After the run, a judge subagent maps each rubric check to action ids and findings lines, and writes `mapping.json`.
   - `score.py` is pure Python. It aggregates `mapping.json`, `-actions.json` and the rubric JSON into pass/partial/fail and bucket counts.
   - Its fixture test uses a hand-written mapping.
2. **Filters vs D5 vs G21.**
   - A scope filter always removes the *test or action*, even for a must-check pattern on a critical flow.
   - What stays is a one-line entry in "Suppressed by your filters". That section is not part of the action list: it doesn't count toward G21 or toward the ≤15 Must+Should cap.
   - The owner sees the risk and decides.
3. **There is no "I".**
   - Buckets come from severity P1/P2/P3. Severity = the pattern's default, adjusted by `severity-calibration.md` with a cited code line.
   - **Must** = P1, any BUG, or P2 on a confirmed critical flow.
   - **Should** = other P2, ≤8.
   - **Highlight** = P3, one line each.
   - In a normal run Must is uncapped, but more than 10 Must items is reported as a warning that tells the owner to narrow scope. The eval criterion ≤15 Must+Should stands.
4. **Authority backfill.**
   - The cap applies only to rules whose `authority` was *classified*. Unclassified rules keep today's behaviour (`authority: unclassified`). Nothing is demoted wholesale.
   - Classification pass: one batched agent pass over the 273 `must` rules and the 234 deterministic rules (they overlap; the union is about 400). It sets `authority` and `external_check` and fixes or demotes conflicts.
   - The remaining `should`/`nice` rules stay unclassified for now.
5. **Order.**
   1. Shared patterns and invariants.
   2. spec-audit phase 1.
   3. `score.py`.
   4. **The pilot-project eval**, on phase 1 only. The new KB domains and the authority cap are not wired into packs yet, so any regression is attributable to phase 1.
   5. `task-qa` and `project-audit`.
   6. KB fixes, classification and new domains. These are wired into packs after the eval.

   The KB agent work can run in parallel with steps 1–3 because it isn't wired in. Cost approvals: the overall budget once (owner), and the pilot-project eval and the task-qa trial separately.
6. **Eval runs.** The same combined Workflows+Templates scope is run twice. Agreement is compared per (entity, pattern-id) cell. `score.py` has an `--agreement run1 run2` mode.
7. **task-qa composition.**
   - It does not invoke `plan-tests` or `cover` as full skills.
   - Their reusable logic (scenario format, depth wording, gap classification, three proofs) moves into a shared reference, `references/test-delta.md`, which all three skills point to.
   - `task-qa` follows that reference inline and invokes `write-tests` only when it writes tests.
   - It reads only the profile sections it needs.
   - Token targets are estimates to be measured in the trial.

## 9. Changes after the branch review (2026-10-19)
- **New cell verdict `SUPPRESSED`.** A filtered cell gets this verdict and goes to *Suppressed by your filters*, not to product questions. The findings template has the section.
- **A BUG test is never made green by an agent.** It stays failing, either uncommitted or with an expected-fail marker. The orchestrator returns to implementation only with the owner's OK.
- **`score.py validate` enforces more.** A test or bug must carry its prescription fields, an N/A cell must have evidence, and a question must sit in the `question` bucket.
- **`render_rules.py` reports dangling rule-id references.**
- **Conflict rules.** The `must` conflicts were rewritten. The remaining conflicts carry a "РАСХОДИТСЯ СО СТАНДАРТОМ" flag in packs.
- **plan-tests uses the buckets.** Its P3 items are Highlight and are not implemented unless promoted.
