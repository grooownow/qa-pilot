# Скилл `qa-pilot:spec-audit` (подпроект C) — дизайн

Дата: 2026-10-12 · Ветка: `feat/book-knowledge-base` · Статус: на ревью
Входные данные:
- свод `knowledge/catalog/` (подпроекты A+B);
- уроки пилота `docs/superpowers/notes/2026-10-12-pawfile-spec-audit-pilot.md`.

## 1. Цель

Скилл проверяет **требования и тест-план** продукта по своду правил (книга «Качество решает всё» плюс собственные правила qa-pilot) и отвечает на три вопроса пользователя:

1. **Каких тест-кейсов не хватает** для этого флоу или фичи?
2. **Насколько хорошо требования готовы** к тестированию: полнота, однозначность, противоречия?
3. **Что в проекте нужно решить** (нефункциональные требования, гейты, спорные места)?

Результат — отчёт с находками P1/P2/P3. Каждая находка привязана к строке документа, к правилу и, если в проекте есть код, к месту в коде. Плюс список недостающих сценариев, готовый к передаче в `plan-tests` и `write-tests`.

**Не цель v1:** аудит кода автотестов (есть `qa-pilot:audit`), аудит живого продукта (есть `qa-pilot:test`), импорт внешних TMS. Это следующие версии, свод к ним уже готов (`applies_to`).

## 2. Требования из пилота (обязательные)

| # | Требование | Откуда |
|---|---|---|
| R1 | **Сверка с кодом обязательна**, если код доступен. Каждый «недостающий сценарий» проверяется grep'ом по тестам: covered или gap. У каждой P1/P2 есть колонка «spec ↔ code» с file:line | ~⅓ кандидатов в пилоте уже были покрыты; все P1 найдены сравнением с кодом |
| R2 | **Модели состояний и таблицы «действие × состояние»** строятся для каждой сущности с жизненным циклом. Каждый переход сверяется с тем, кто его записывает | Лучшие находки пилота (TD-039/040/031) |
| R3 | **Инвариант во всех путях записи:** для каждого правила валидации перечислить все пути записи | Повторяющийся класс дефектов (F12, F05) |
| R4 | **Противоречия между документами:** спека ↔ соседние спеки ↔ решения ↔ собственные разделы «Изменения» ↔ блок AC | Самый массовый класс находок |
| R5 | **Детерминированная проверка без шума:** только строки требований и AC; пропуск цитат, кода, rationale, history, open questions; словарь расширяется проектом | 15 из 16 ложных срабатываний REQ-014 |
| R6 | **Анти-false-green для security-AC:** найти тест, который проверяет конкретный отказ, и убедиться, что mock не фиксирует успех | P1 по rate-limit удаления |
| R7 | **Нефункциональные проверки — один раз на проект**, а не на каждую спеку | g5 пилота |
| R8 | **Фильтр правил по профилю продукта** (web, PWA, native, деньги, стиль API…) | Шум от REST-, мобильных и денежных правил |
| R9 | **Калибровка:** `must` книги ≠ P1. P1 только при реальном дефекте, проблеме с данными или безопасностью, отсутствии регресс-гейта | Пилот |
| R10 | **Решения проекта приоритетнее книги:** `docs/decisions`, CLAUDE.md, decision-поля в своде, оверрайды проекта | Раскрытие аккаунта в pawfile |
| R11 | **Экономия токенов:** пилот на весь проект стоил ≈1 млн токенов субагентов. По умолчанию — одна фича или флоу; полный прогон только по явному запросу и с предупреждением о стоимости | Claude Pro — целевой план плагина |

## 3. Раскладка файлов

```
skills/spec-audit/
  SKILL.md                    # фазы скилла (англ., как остальные скиллы)
  scripts/
    rules_pack.py             # профиль + цели → компактный пакет правил (md)
    spec_lint.py              # детерминированные проверки текста спек
    test_rules_pack.py
    test_spec_lint.py
references/
  spec-audit-lenses.md        # линзы анализа и формат находок для агентов
  severity-calibration.md     # как ставить P1/P2/P3 (общий для будущих аудитов)
knowledge/
  catalog/                     # как есть (A+B)
  qa-pilot/rules/*.json       # собственные правила qa-pilot (QAP-…), та же схема
```

В проекте пользователя:

```
docs/qa/project-profile.md         # +секция «Product traits» (добавляет onboard; если её нет, spec-audit спросит и допишет)
docs/qa/rule-overrides.json        # опционально: отключённые правила, решения, доп. слова, свои правила PRJ-…
docs/qa/spec-audit/<date>-<slug>.md  # отчёт
```

Python-скрипты используют только стандартную библиотеку. Если `python3` нет, скилл выполняет те же шаги вручную по описанию в SKILL.md: медленнее, но работает. Скилл сообщает об этом пользователю.

## 4. Профиль продукта и фильтр правил (R8)

В `project-profile.md` добавляется секция **Product traits**:

```yaml
platform: [web, pwa]            # web | pwa | ios | android | desktop | game
api_style: [server-actions, rpc] # rest | graphql | soap | server-actions | rpc
has_payments: false
has_auth: true
has_user_uploads: true
i18n: true
rtl: false
regulated: [gdpr]               # gdpr | hipaa | pci | eaa | none
```

`rules_pack.py` берёт свод (`knowledge/catalog`, `knowledge/qa-pilot` и правила проекта `PRJ-*`), цели аудита (`requirements`, `test-plan`) и черты продукта. На выходе:

- компактный пакет `<scratch>/packs/*.md`: строка на правило, решения проекта подставлены, отключённые правила выброшены;
- `manifest.json`: какие темы и теги исключены и почему.

Таблица «черта → исключение» лежит в `rules_pack.py` как данные. Примеры:
- нет `ios` → исключить `mobile-hig`;
- нет `game` → `games`;
- `has_payments: false` → теги `payments`, `subscription`, `pricing`;
- в `api_style` нет `rest` → правила с тегом `rest-status`.

Чтобы эти исключения работали, правилам в своде проставляются недостающие теги (`payments`, `rest-status`, `native-only` и т.п.). Это часть реализации, делается одним проходом по JSON.

## 5. Фазы скилла

**Фаза 0 — Preflight.**
- Прочитать профиль: если его нет, предложить `onboard`. Если нет Product traits, спросить их одним сообщением и дописать.
- Прочитать `rule-overrides.json`, CLAUDE.md и `docs/decisions/*`.
- Согласовать скоуп. По умолчанию — одна фича или флоу: файлы спек, тикет или описание. Режим «весь проект» — только по явному запросу, с оценкой стоимости: N документов × ~40k токенов (для pawfile ≈1 млн, по данным пилота).
- Создать отчёт-заготовку. Дальше всё пишется в него по ходу работы.

**Фаза 1 — Пакет правил и детерминированные проверки.**
- `rules_pack.py` собирает пакеты правил.
- `spec_lint.py` прогоняет детерминированные проверки по скоупу (R5):
  - расплывчатые слова (словарь REQ-014 + `extra_vague_words` проекта, по умолчанию плюс «корректно/корректный»);
  - маркеры незавершённости (`TBD`, `TODO`, `???`, «ЧЕРНОВИК», «уточнить»).

  Проверяются только строки внутри разделов требований и AC. Пропускаются кавычки «…» и "…", код, разделы с заголовками rationale, history, «Изменения», open questions, «Открытые решения». Паттерны заголовков настраиваются.
- Вывод — JSON с файлом, строкой, правилом и фрагментом. Результаты попадают в отчёт как «кандидаты»; финальное решение принимает фаза 4.

**Фаза 2 — Анализ документов (агенты).**
- Документы группируются по кластерам фич. На кластер — один агент, но не больше 5 параллельно.
- Агент получает инструкцию из `references/spec-audit-lenses.md` и применяет линзы по порядку:
  1. сущности с жизненным циклом → модель состояний и таблица «действие × состояние» (R2);
  2. комбинации условий → таблица решений;
  3. каждый вход и лимит → классы эквивалентности и 3BVA;
  4. противоречия: внутри документа, с соседями, с решениями (R4);
  5. состояния ошибки, пустоты и загрузки, предугадывание ошибок;
  6. доменные пакеты правил по чертам продукта.
- Находки пишутся в файл кластера по ходу работы. Формат таблицы — как в пилоте, плюс колонка `code`.
- Модель агентов — модель сессии (это суждение, см. `model-routing.md`).

**Фаза 3 — Сверка с кодом.** Обязательна, если код доступен. Делают её те же агенты внутри своей фазы, по инструкции:
- для каждого недостающего сценария — grep по `*.test.*`, `*.spec.*` и интеграционным тестам; результат: covered (путь) или gap (R1);
- для каждого инварианта — список путей записи и проверка в каждом (R3);
- для каждого security-AC — тест с конкретным кодом отказа и без mock, который фиксирует успех (R6);
- для каждого утверждения спеки «X есть / нет в коде» — проверка (дрейф).

**Фаза 4 — Проектные нефункциональные проверки (R7).** Один проход в главной сессии, не по каждой спеке:
- целевой уровень WCAG;
- поддерживаемые браузеры и устройства (плюс projects в `playwright.config`);
- бюджет Core Web Vitals;
- офлайн-поведение PWA;
- таймауты;
- регресс- и smoke-гейт: триггеры CI, Definition of Done в CLAUDE.md.

Каждая проверка — правило из свода, результат — находка или «ок».

**Фаза 5 — Триаж (главная сессия, не делегируется).**
- Каждая P1 и топ-P2 проверяются по коду лично (правило CLAUDE.md пользователя). Ложные выбрасываются явно, со списком в приложении.
- Калибровка по `references/severity-calibration.md` (R9).
- Дедупликация между кластерами.
- Решения проекта: сработавшее, но отменённое решением правило попадает в «Skipped as project decision» (R10).

**Фаза 6 — Отчёт и передача.** Структура отчёта — как в пилоте:
1. шапка: скоуп, черты продукта, применённые пакеты, стоимость;
2. итоговая таблица;
3. P1;
4. топ-P2;
5. сквозные выводы;
6. **решения, нужные от владельца**;
7. полные находки по документам;
8. приложение: отброшенные кандидаты и ложные срабатывания lint.

По запросу пользователя недостающие сценарии выгружаются в `docs/qa/test-plans/<feature>.md` в формате `plan-tests`, чтобы дальше работал `write-tests`. Это стык с подпроектом D. Спеки проекта скилл **не правит**.

## 6. Собственные правила qa-pilot (пробелы каталога)

`knowledge/qa-pilot/rules/*.json` использует ту же схему, что и свод книги, с тремя отличиями:
- id `QAP-<TOPIC>-NNN`;
- вместо `source.chunk_id` указывается `source.origin`, например «pilot pawfile 2026-10-12»;
- язык — русский, как у свода.

`render_rules.py` учит оба источника.

Первые пять правил — из пилота:
1. деградация инфраструктуры: fail-open или fail-closed у лимитеров и внешних зависимостей;
2. окно после отзыва сессии при локальной проверке JWT;
3. парные guard'ы проверяются каждый по отдельности;
4. часовой пояс «сегодня» в валидации дат и сроков;
5. внутренние идентификаторы не утекают через публичные эндпоинты: тело RPC сверяется с заявлениями спеки.

Правила проекта (`PRJ-*`) живут в `rule-overrides.json` пользователя, в той же схеме.

## 7. `rule-overrides.json`

```json
{
  "disabled": ["QAC-ART-004"],
  "decisions": { "QAC-REQ-014": "…текст решения…" },
  "extra_vague_words": ["корректн", "нормальн"],
  "skip_section_patterns": ["^#+\\s*(Rationale|История|Изменения)"],
  "rules": [ /* PRJ-… записи в схеме свода */ ]
}
```

Скилл не создаёт этот файл молча. Он предлагает добавить запись, когда пользователь в ходе триажа говорит «это у нас осознанно».

## 8. Проверка качества самого скилла

- **Юнит-тесты скриптов** (stdlib `unittest`):
  - фильтр по чертам;
  - подстановка решений;
  - отключение правил;
  - lint: срабатывает в AC, молчит в цитатах, коде, rationale и «Изменениях»;
  - доп. слова;
  - маркеры незавершённости.
- **Регрессионный eval на pawfile** (ручной прогон, результат — в notes). Скилл в режиме «весь проект» на том же коммите pawfile должен:
  - найти все 3 причины P1 из пилота;
  - дать ≤ 2 ложных срабатываний lint (в пилоте было 15);
  - пометить «covered in code» не меньше кандидатов, чем пилот.
- **Eval на одной фиче** (режим по умолчанию): F06 pawfile. Время и токены записываются; цель — ≤ 150k токенов на фичу.
- Валидатор свода проходит с QAP-правилами; `check_overlap.py` по-прежнему 0.

## 9. Вне скоупа C (следующие шаги)

- **D — встраивание:**
  - `plan-tests` выбирает техники и чек-листы из свода по типу сценария;
  - `cover` запускает облегчённый spec-audit (только lint + линзы 1–3) на изменённые спеки;
  - `audit` подтягивает test-code-правила.
- Цели `test-code`, `live-product`, `test-cases` для spec-audit.
- Автоправка спек.

## 10. Риски

- **Стоимость.** Полный прогон дорогой. Смягчение: режим по умолчанию — одна фича; оценка стоимости показывается до запуска; пакеты правил отфильтрованы.
- **Шум доменных правил** при плохо заполненном профиле. Смягчение: Product traits спрашиваются явно, `manifest.json` в отчёте показывает, что исключено.
- **Устаревание свода.** Правила с `modern_note` датированы, обновление свода — отдельный процесс (пересборка и сверка).
