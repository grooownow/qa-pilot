# qa-pilot 0.9.0 — harness fit, strategy check, UI testing, budget — design

Date: 2026-10-27 · Status: approved for building (owner answered the open question; calls below are Claude's). Calls marked **(Claude's call)** are mine; the rest is the owner's.
Branch: `feat/0.9.0` (from `main` v0.8.1). Already on it: the hard `data-testid` locator rule (commit 68bcfbb).

## Intent

qa-pilot plans, verifies and audits tests well inside a task. It is weak at the level above the task:

- it does not look at the project's **harness** (orchestrators, review/test steps, hooks) and so never says where its
  steps belong, or that without a harness the owner has to call it by hand;
- on a project that already has tests it rates the **framework** (9 maturity areas) but does not judge the project's
  **test strategy**: which layers are missing for the kind of code it has, whether its own test rules are sound;
- it has nothing on **UI / component testing**: a component library with Storybook is a test layer of its own, between
  unit and e2e, and qa-pilot ignores it;
- it never asks how much the owner wants to **spend**: one audit can cost hundreds of thousands of tokens;
- a layer that runs only locally is noted in the profile, but the owner is not told plainly that CI does not run it.

The owner's goal: tune the plugin "to the ideal" first, then split it into the Agensi Free and Pro editions. Every
item below is marked with its edition, so the split later is a cut, not a redesign.

## Goals

1. **Harness scan in onboard** (Free). Find orchestrators and quality steps, record them in the profile, propose
   where qa-pilot steps fit, with a ready snippet. Never edit them.
2. **Fit estimate in onboard** (Free). A short grade of how well qa-pilot will work on this project and what holds it
   back, derived from what onboard already found.
3. **Budget question in onboard** (Free). The owner picks a spending mode; heavy skills respect it.
4. **Strategy check** (Free). Empty project → the roadmap (exists) plus an offer of an e2e skeleton. Project with
   tests → a short, rule-backed verdict on the strategy and the project's own test rules.
5. **UI testing** — a bottom-up strategy for component libraries:
   - onboard detects the library, Storybook and its tests and writes a one-line state (Free);
   - a new deep audit `qa-pilot:ui-test-audit` inventories atoms and compositions, finds gaps, and with a yes writes
     stories and interaction tests (Pro).
6. **CI gaps stated plainly** in every report (Free): "these layers do not run in CI, so they are not coverage".
7. **Test data and isolation, accessibility** get explicit checks (Free).

## Non-goals

- No CI setup by the agent: qa-pilot says CI is missing and what to run; the owner (or their agent) sets it up.
- No editing of another project's orchestrator or rules files.
- No exact token accounting (see §3: the agent cannot read its own usage).
- No visual-regression service integration (Chromatic, Percy); only guidance on when snapshots are worth it.
- No Free/Pro packaging in this release; only edition marks in this document and in the CHANGELOG.

## Anti-goals

- Onboarding that turns into a 200k-token audit. Onboard additions must stay cheap: they reuse what Phase 1 already
  read; the strategy check reads at most the project's test-rule docs and a few test files.
- A fit grade that sounds like marketing or blames the owner. It names mechanisms: "no test command found → qa-pilot
  cannot run tests, verify will only read them".
- UI tests that duplicate atom tests inside every composition.
- A budget mode that silently drops checks. Whatever a cheaper mode skips is listed in the report as "not done".

## Installing tools (owner, 2026-10-27)

The two setup modes — the e2e skeleton (§4) and the UI-test setup (§5.3, state 1) — **install tools themselves after
an explicit yes**. Before installing, the agent shows the exact list: packages with versions, commands it will run
(package manager install, browser download such as `npx playwright install chromium`), and files it will create or
edit (`package.json`, the lockfile, configs). Only after the owner's yes to that list does it run them. Then it runs
the first test and shows it can fail (the failure proof). Without a yes it writes nothing and stops at the list. A
yes covers that list only; anything added later is asked again. It never installs globally and never touches CI.

## 1. Harness scan (onboard, new Phase 1 item + profile section) — Free

**What counts as harness**, searched cheaply (file names and headings, not whole files):

- agent workflows: `.claude/skills/*/SKILL.md`, `.claude/commands/*.md`, `.claude/agents/*.md`, `AGENTS.md`,
  `CLAUDE.md` sections that describe a task flow, `.cursor/rules/**`, `.github/copilot-instructions.md`;
- hooks: `.claude/settings*.json` `hooks`, git hooks (`.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`);
- review and quality steps in CI: review bots (CodeRabbit, Danger), required checks, PR templates with a QA section.

For each workflow found: its phases (from headings), and whether a phase matches one of qa-pilot's points:
"before the plan is approved" → `task-qa plan`; "after implementation / tests, before review or PR" → `task-qa verify`;
"periodic / release" → `/qa-pilot:audit`. The snippets come from `references/orchestrator-integration.md` (it gains
a generic snippet next to the example one).

**Profile section** `## Harness` (facts only) — table: workflow · path · phases · fit point (or "none fits"). Plus one
line "How qa-pilot is called here": `orchestrator <name>` or `manually` when nothing was found. The proposed steps and
snippets are recommendations, so they go to `docs/qa/strategy-check.md` (§4), not the profile **(Claude's call)**.
Harness paths are checked by `profile_drift.py` (a workflow file that disappeared is `missing-path`).

**Onboard output:** the proposals are shown once at the end of onboard, with the snippet; the owner pastes them.

**No harness found:** the profile says `manually`, and onboard's closing message gives the minimal habit: before
coding `/qa-pilot:test <ticket>` (plan), after coding `/qa-pilot:test` (verify), and runs the regression set locally
before the PR. That is enough for qa-pilot to work; the fit estimate (§2) says what is lost (nobody calls verify
automatically).

## 2. Fit estimate (onboard, new profile section) — Free

`## qa-pilot fit` (in `docs/qa/strategy-check.md`, §4) — one grade: **full / partial / limited**, then one line per limiting factor: factor · effect on
qa-pilot · what would fix it. No new scanning: the inputs are what onboard already has.

| Factor | Effect when missing |
|---|---|
| a runnable test command | verify and the failure proof only read tests, never run them |
| tests run in CI | coverage claims are "local only"; a test can rot unnoticed |
| a test-id convention (or the hard rule accepted) | new tests need component edits; more fallback locators |
| a network-mock seam | UI tests need a real backend; slower, flakier |
| a harness fit point | plan/verify happen only when someone remembers |
| tracker access | AC come from pasted text only |
| answered critical flows | audits cannot prioritise; everything is "standard" |
| open blocking gaps | named one by one |

Grade rule **(Claude's call)**: full = no factor missing; partial = 1–3 missing and a runnable test command exists;
limited = no runnable test command, or 4+ missing. Onboard refresh re-runs the harness scan and the fit estimate
(both cheap) and rewrites them; the strategy check (§4) is re-run only when asked or when the drift check reported
`new-test-dep` / `rules-changed` **(Claude's call)**.

## 3. Budget mode (onboard question + every heavy skill) — Free

Onboard Phase 2 asks one more question: how to spend.

- **economy** — smallest depth everywhere; before any run estimated over ~150k tokens, show the estimate and ask;
- **standard** (default) — today's behaviour;
- **thorough** — `standard` depth for audits, larger probe samples.

Stored in the profile as `## Budget` → `mode: economy|standard|thorough`, plus `report_spend: yes|no`.

What a mode changes (table in a new `references/budget.md`, read by every skill that has a "Budget" paragraph today).
**`standard` is exactly today's behaviour** **(Claude's call)**; only economy and thorough differ:

| Knob | economy | standard (today) | thorough |
|---|---|---|---|
| standalone spec-audit default depth | critical | standard | thorough |
| spec-audit inside project-audit | critical | critical | standard |
| project-audit default flows | 1 | 3 | 5 |
| failure-probe sample (project-audit) | 3 | up to 10 | up to 20 |
| test-code-audit probe sample | critical flows only | critical flows + suspects | + one per suite |
| review-loop rounds | 1 | today's cap | today's cap |
| ui-test-audit components per run | 10 | 30 | all | Anything a mode skipped is listed under "Not done (budget)" in the report.

**Spend reporting.** The agent cannot read its own token count. With `report_spend: yes`, each heavy skill states
its own estimate before and an estimate after ("~120k by the size of what was read"), and points the owner to
Claude Code's `/cost` (or `/usage`) for the real number **(Claude's call)**.

## 4. Strategy check (onboard Phase 5, cheap; project-audit reuses it) — Free

**Empty project** (no test files, or only framework boilerplate): the profile marks `Framework maturity` as mostly
missing; onboard says so and points to `/qa-pilot:audit` for the roadmap (exists). New: it offers an **e2e
skeleton** whenever the project has **no e2e layer** — empty or with unit tests only **(Claude's call)**. Framework: the
one the project already depends on, else Playwright. If an e2e runner exists with its own config, there is no
skeleton; the strategy check reports gaps instead. The skeleton — after a yes, `write-tests` (new mode `bootstrap`) adds: the framework config, an auth fixture, a base
page object, the cleanup fixture from `e2e-patterns.md`, a test-id constants file, one smoke test on the first
critical flow, and the package script. CI is not touched; the closing message says what job to add. (Owner: "the
roadmap is the necessary minimum", the skeleton is an offer.)

**Where results live** **(Claude's call)**: the profile stays "facts only" and keeps its size limit. Recommendations go
to a new file `docs/qa/strategy-check.md`, which the profile links to: `## qa-pilot fit` (§2), `## Harness proposals`
(§1), `## Strategy check` (this section), `## UI state` (§5.2). Each section carries its own `Generated … on <date>`
line and is replaced whole when its step re-runs, so a section kept from an earlier run shows its real age (changed
during the final review).

**Project with tests:** a short verdict, max **8 findings**, each backed by a rule id, written to
`docs/qa/strategy-check.md` under `## Strategy check` and shown at the end of onboard. Inputs: the maturity table, `Test layers`, the project's own test
rules (the docs and `CLAUDE.md` sections Phase 1 linked under Conventions), and 3–5 test files per layer. Checks:

- **layer fit:** logic-heavy modules (services, utils, reducers) with no unit tests; UI library with no component
  tests (§5); everything only in e2e (QAP-TC-030, QAP-TS-014);
- **own rules vs qa-pilot rules:** a project rule that contradicts a must rule (e.g. "use CSS selectors",
  "waitForTimeout is fine") is a finding with both texts; a missing rule area (no e2e rules at all, no locator
  policy, no test-data rule) is a finding;
- **CI:** layers not run in CI (§6);
- **test data and isolation:** shared accounts, no cleanup, order-dependent suites (QAP-TC-020, e2e-patterns);
- **accessibility:** no automated a11y check anywhere (axe in e2e, `addon-a11y` in Storybook) on a product with
  public UI.

Output per finding: area · what we saw (path) · rule id · the one change that fixes it. Then one line per layer:
`unit / component / e2e / visual / a11y — ok / weak / missing`. Budget: about 30–50k tokens on top of onboard.
`project-audit` Phase 1 reads this section instead of recomputing it and turns findings into roadmap items.

If the project has its own complete rules, the check records "project rules adopted" and only lists contradictions;
qa-pilot then works by the project's rules (`quality-rules.md` rule 6, as today).

## 5. UI testing

### 5.1 The strategy (new `references/ui-testing.md`, used by onboard, ui-test-audit, write-tests)

Bottom-up, from the owner:

1. **Atoms** (library components that use no other library component): stories for every state (variants, sizes,
   disabled, loading, error, empty, long content, focus) and interaction tests for every behaviour (click, keyboard,
   open/close, validation, controlled/uncontrolled value).
2. **Compositions** (library components built from atoms): tests only for what the composition adds — wiring,
   state passed between atoms, its own logic. Atom behaviour is not tested again.
3. **E2E:** complex UI behaviour that needs the real app (routing, data) is checked as a step inside an e2e flow, not
   as a separate UI test.

Tooling defaults when the project has none **(Claude's call)**: Storybook with interaction tests in `play` functions
run by the Storybook Vitest addon (browser mode, Playwright provider); `addon-a11y` for accessibility. If the project
already uses the Storybook test-runner or Playwright component tests, keep them. Visual snapshots: only for stable,
deterministic components, only where CI renders in a pinned environment; never as the only assertion (QAP-TC-024).
Locators inside stories follow the hard test-id rule.

New rules in `knowledge/qa-pilot/rules/` (new file `ui-testing.json`, ids `QAP-UI-NNN`): one per point above, plus
"a composition test does not re-test atom behaviour" and "every story state that has behaviour has a play test".

### 5.2 Onboard (Free)

Phase 1 detects: a component library (`packages/ui`, `src/components/ui`, `components.json` of shadcn, a design-system
package), Storybook (`.storybook/`), story count, stories with `play`, the runner, and whether CI runs it. The profile
`Test layers` gets a `component/UI` row; the fit estimate and the strategy check use it. One line in onboard's close:
"UI library: N components, M with interaction tests; run `/qa-pilot:audit ui` for the gap list" — the deep audit is
Pro.

### 5.3 `qa-pilot:ui-test-audit` (new internal skill) — Pro

Called by `/qa-pilot:audit ui` (new routing words: "ui", "storybook", "компоненты", "UI-тесты", "библиотека
компонентов").

- **Inventory** (deterministic, new stdlib script `ui_inventory.py`): components in the library, which library
  components each imports (→ atom or composition), stories per component, stories with `play`, story states named.
- **Three project states:**
  1. library, no UI tests → setup recommendation with exact steps for this repo (tooling default above), a CI line,
     and an ordered list: atoms first;
  2. some tests, no clear strategy → gap table per component (missing states, missing behaviours, compositions that
     re-test atoms), ordered atoms → compositions;
  3. tests and the project's own UI-test rules → adopt them, rate them against `ui-testing.md` (contradictions
     only), agree with the owner, then work by them.
- **Output:** `docs/qa/ui-test-audit-<date>.md` + an action list in the existing actions format.
- **Writing:** with the owner's yes, `write-tests` (new target kind `story`) writes stories and `play` tests for the
  top gaps, under the auto-test guard and the failure proof (a `play` test must fail when the behaviour is broken).
  Rows go to the coverage matrix with layer `component`.
- Budget: components per run by mode (§3).

## 6. CI gaps in every report — Free

Every report-writing skill (task-qa verify block, cover summary, audits) ends with one line when the profile has
layers not run in CI: "Not in CI: <layers>. These tests count as local only." `project-audit` keeps the blocker rule.
No CI drafting **(Claude's call)**: the owner said saying it is enough. The minimum the line recommends: run the
regression set locally at the end of each task (the orchestrator's finalize step, or by hand).

## 7. Test data, isolation, accessibility — Free

Test data and isolation already exist as a maturity area and in `e2e-patterns.md` (cleanup fixture, test data
management). New: the strategy check (§4) names them, and `write-tests` refuses to add a test that uses a shared
account or depends on another test's data without a comment saying why. Accessibility: `e2e-patterns.md` gains a
short "Accessibility check" section (axe scan of each critical-flow page in the smoke set, violations of impact
serious/critical fail); the strategy check and the UI audit use it.

## Constraints

- Instructions first; scripts only where counting is deterministic (`ui_inventory.py`), stdlib, unit-tested.
- All gates stay green; `check_skills.py` passes (new skill: description ≤ 1024 with a "Not for" naming a sibling).
- New profile sections are added to `profile_drift.py` only if they hold paths or commands (Harness paths: yes).
- Release 0.9.0: CHANGELOG, version bump, tag; push only with the owner's OK, via the SSH alias.
- Copy tone: mechanism, no hype; the author of the book catalog is never named.
