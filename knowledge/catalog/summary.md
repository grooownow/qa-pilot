# «Качество решает всё» — краткое содержание и польза для qa-pilot

**Объём:** 819 страниц. Значительную часть занимают скриншоты, текста около 113 тыс. слов.
**Жанр:** практическое руководство по **ручному** тестированию и инженерии качества, написанное жёстко и с реальными кейсами. Автоматизации тестов в книге нет совсем, это позиция автора. Глубокой безопасности тоже нет: автор честно говорит, что проверял её только косвенно.

## Чем книга полезна qa-pilot

1. **Детерминированные проверки артефактов.** Книга чётко говорит, что должно быть в тест-кейсе, баг-репорте, тест-плане и отчёте, и какие слова в требованиях запрещены. Такие проверки можно делать скриптом или регуляркой, без суждения агента. Это основа будущего скилла аудита.
2. **Полнота тест-плана через техники тест-дизайна.** Классы эквивалентности, граничные значения в варианте 3BVA, pairwise, таблицы решений, состояния и переходы, предугадывание ошибок. По ним `plan-tests` сможет проверять, все ли сценарии есть у фичи.
3. **Готовые чек-листы для живого продукта:** формы, GUI, локализация, мобильные прерывания, инсталляция, API (BINMEN/POISED), доступность по WCAG, тёмные паттерны.
4. **Правила для самого ИИ-агента.** Автор прямо перечисляет, где ИИ ошибается: не умеет строить pairwise-покрытие, теряет граничные значения, выдумывает несуществующие элементы, теряет нить в длинном диалоге. Эти пункты стали обязательными правилами для qa-pilot (тема `ai-in-qa`). Любопытная деталь: в конце главы автор пишет, что пока не существует ИИ, который проверял бы каждую фичу сразу по WCAG, HIG, Material, W3C и законам UX. Этот свод — шаг ровно в эту сторону.
5. **Современные оговорки.** Там, где практика изменилась, в правило добавлено поле `modern_note`: INP вместо FID, WCAG 2.2, App Store 4.8, правило FTC «click to cancel», k6.

## Что спорно, устарело или вне скоупа

- **Автоматизации тестов нет.** Как писать надёжные автотесты, книга не говорит; это по-прежнему зона `references/` qa-pilot. Из книги мы берём, *что* проверять.
- **Внутренние противоречия.** При сверке нашли три:
  - очищать ли поле пароля после ошибки (QAC-FORM-029 против QAC-UX-028);
  - можно ли блокировать кнопку подтверждения в диалоге (QAC-MD-055);
  - как центрировать 3BVA (уточнено в QAC-TD-008).

  По первым двум команда приняла решение (поле `decision`): пароль после ошибки **не очищается**, кнопка подтверждения в диалоге **не блокируется**. Третье противоречие разобрано в самой записи.
- **Фактические ошибки автора** исправлены в `modern_note`, текст книги при этом пересказан как есть:
  - среднее по целым числам в PostgreSQL;
  - инвертированный порог в примере k6;
  - несуществующая команда `adb shell am recover-prep`;
  - детали критериев WCAG 2.5.5 и 2.4.13.
- **Скриншоты не извлекались.** Где смысл держится на картинке, правило построено только по тексту.
- **Тон.** Книга резкая и местами нецензурная. В своде формулировки нейтральные.

## Известные расхождения со стандартами

`verification: ok` означает **верность пересказу книги**, а не корректность по стандартам. Независимое ревью книги (`docs/superpowers/notes/2026-10-19-book-independent-review.md`) нашло 48 расхождений с ISTQB v4, RFC, W3C и NIST.

**Внешняя сверка 2026-10-19.** Проверены 427 правил: все `must` и все детерминированные. Ход и итог сверки — в `docs/superpowers/notes/2026-10-19-kb-external-check.md`.
- Каждому проверенному правилу проставлены `authority` (на чём держится) и `external_check` (`aligned` или `conflict`).
- Остальные правила пока `unclassified`.

**Что исправлено:**
- **QAC-API-085**: RFC 9110 разрешает игнорировать Accept;
- **QAC-TD-008**: ISTQB допускает 2BVA;
- **QAC-FORM-004**: одно поле для полного имени.

**Цифры книги — не стандарт.** Помечены как `author-opinion`:
- 56% багов из требований;
- кривая 1–10–100;
- 80/20;
- проценты «покрытия багов» у pairwise;
- «отраслевые» пороги времени отклика.

Использовать их как критерий pass/fail нельзя.

**В пакетах аудита** `must`-правило с `authority` = `author-opinion` или `vendor-guideline` показывается как `should`.

## Топ-15 жёстких правил (по ценности для аудита)

1. **QAC-REQ-014.** В требованиях нет размытых слов: «быстро», «удобно», «интуитивно», «при необходимости». Проверяется регуляркой.
2. **QAC-ART-004.** У тест-кейса заполнены все обязательные атрибуты.
3. **QAC-ART-013.** Тест-кейсы не зависят друг от друга.
4. **QAC-ART-052.** Ожидаемый результат конкретен, без формулировок вроде «работает штатно».
5. **QAC-ART-047 и ART-050.** В баг-репорте есть все атрибуты, а окружение указано с версиями.
6. **QAC-ART-038.** В отчёте о тестировании есть явная рекомендация по релизу.
7. **QAC-TD-001.** Каждый класс эквивалентности покрыт.
8. **QAC-TD-007 и TD-009.** Граничные значения проверяются на каждом стыке классов; для длины поля проверяются min−1…max+1.
9. **QAC-TD-024 и AI-032.** Pairwise-набор полный и построен инструментом (PICT), а не LLM.
10. **QAC-TD-040.** Проверены недопустимые события в каждом состоянии.
11. **QAC-API-014.** Ошибка не возвращается как 200 OK.
12. **QAC-API-088, API-089 и API-128.** Данные недоступны без авторизации; сервер не доверяет флагам, которые присылает клиент; через API нельзя изменить чужие данные.
13. **QAC-FORM-010.** После ошибки валидации введённые данные не сбрасываются.
14. **QAC-A11Y-002.** Целевой уровень — WCAG AA, проверка идёт по каждому критерию.
15. **QAC-UXL-022.** Тёмный паттерн — это дефект, и о нём нужно сообщать.
