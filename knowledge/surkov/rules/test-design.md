# test-design

Сгенерировано из `test-design.json` скриптом `scripts/kb/render_rules.py` — правьте JSON, не этот файл.
Формулировки — пересказ книги Р. Суркова «Качество решает всё»; страницы — печатные номера книги.

## Жёсткие правила (13)

### SRK-TD-001 · Каждый вход разбит на классы эквивалентности, и каждый класс покрыт

`must` · проверка: эвристика агента · для: test-plan, test-cases, test-code · источник: `s1-c09-02`, с. 70–71

Для поля или параметра с правилами из требований выделяют классы, где система ведёт себя одинаково: валидный(е) и невалидные ниже и выше допустимого диапазона, и берут хотя бы одно значение из каждого класса.

**Как проверить:** Из требований выписать диапазоны/категории для каждого входа и построить классы (включая отрицательные/нулевые и выше максимума). Для каждого класса найти в плане/кейсах/параметрах автотеста хотя бы одно значение. Класс без представителя — fail (например, для возраста 18–100 нет значения ≤0 или >100).

### SRK-TD-002 · Внутри класса эквивалентности достаточно одного значения

`should` · проверка: эвристика агента · для: test-plan, test-cases, test-code · источник: `s1-c09-02`, с. 70

Не тратить проверки на несколько значений из одного класса с одинаковым ожидаемым результатом: одно значение представляет весь класс (граничные точки — отдельная история).

**Почему:** Цель тест-дизайна — минимум проверок при максимальном покрытии.

**Как проверить:** Сгруппировать сценарии по классам; флаг избыточности, если в одном классе несколько не граничных значений с одинаковым ожидаемым результатом (например, 25, 30 и 50 для диапазона 18–100).

### SRK-TD-003 · Требования определяют поведение для всех классов, включая невалидные

`should` · проверка: эвристика агента · для: requirements · источник: `s1-c09-02`, с. 70

Требование с диапазоном значений должно описывать результат для каждого класса: допустимого, ниже минимума, выше максимума, — с текстом сообщений об ошибке; иначе классы уточняют у аналитика до тестирования.

**Как проверить:** Для каждого числового/длинового ограничения в требованиях проверить, что описано поведение за пределами диапазона (≤0/отрицательные, >max) и текст ошибки. Отсутствие — находка «неполное требование», вопрос аналитику.

### SRK-TD-007 · Граничные значения проверяются на каждом стыке классов

`must` · проверка: эвристика агента · для: requirements, test-plan, test-cases, test-code · источник: `s1-c09-03`, с. 72–73

Границы лежат на стыках классов эквивалентности, и именно там чаще всего ошибаются разработчики (off-by-one). Для диапазонов возраста 1–17/18–100 это 0, 1, 17, 18, 100, 101.

**Как проверить:** Агентом выписать из требований все стыки классов: последнее значение нижнего класса L и первое значение верхнего F (например, 17 и 18). Затем механически сверить со значениями в плане/кейсах/параметризации автотестов: для каждого стыка должны присутствовать и L, и F. Отсутствующее значение — fail с указанием стыка.

### SRK-TD-009 · Поле с ограничением длины: min−1, min, min+1, max−1, max, max+1 символов

`must` · проверка: эвристика агента · для: test-plan, test-cases, test-code, live-product · источник: `s1-c09-03`, с. 73–74

Для строкового поля с длиной от min до max применяют 3BVA к обеим границам допустимого класса: min−1, min, min+1 и max−1, max, max+1 символов. Например, для имени пользователя 3–15 символов (пример из раздела о классах) это 2, 3, 4, 14, 15, 16.

**Как проверить:** Агентом найти в требованиях ограничения длины, вычислить {min−1, min, min+1, max−1, max, max+1} и сверить с длинами строк в тестовых данных (в автотестах — в т.ч. генерируемые строки вида `'a'.repeat(n)`). Отсутствие любой длины — fail. В live — ввести строки этих длин и сверить приём/отказ.

### SRK-TD-010 · Шаг соседних точек равен точности значения

`should` · проверка: эвристика агента · для: test-plan, test-cases, test-code · источник: `s1-c09-03`, с. 75–77

Соседи границы берутся с минимальным шагом представления величины: 1 для целых, 0.01 для денег, 0.01 Мб (≈10 Кб) для размера файла.

**Как проверить:** Для денежных порогов проверить наличие значений ±0.01 от границы (например, 999.99 / 1000.00 / 1000.01); для целых — ±1; для размеров файла — шаг не грубее 0.01 Мб. Соседи с шагом крупнее точности (например, 990 и 1010 для порога 1000) — fail.

### SRK-TD-022 · Перед комбинаторикой значения сжимаются классами эквивалентности

`should` · проверка: эвристика агента · для: test-plan, test-cases, test-code · источник: `s1-c09-04`, с. 78–79

Прежде чем комбинировать параметры, большие наборы значений сворачивают в классы (например, тысячи валидных номеров — один класс «валидный» плюс «невалидный»).

**Как проверить:** Проверить входные параметры комбинаторного набора: флаг, если параметр содержит множество значений одного класса вместо представителей классов.

### SRK-TD-024 · Pairwise-набор полон: каждая пара значений встречается хотя бы раз

`must` · проверка: детерминированно · для: test-plan, test-cases, test-code · источник: `s1-c09-04`, с. 80–82

В попарном наборе каждое значение любого параметра хотя бы один раз сочетается с каждым значением любого другого параметра.

**Как проверить:** Скриптом: для всех пар параметров (Pi, Pj) построить множество требуемых пар значений и проверить, что каждая встречается хотя бы в одной строке набора. Любая непокрытая пара — fail с перечислением.

### SRK-TD-025 · Любой комбинаторный набор использует каждое значение каждого параметра

`must` · проверка: детерминированно · для: test-plan, test-cases, test-code · источник: `s1-c09-04`, с. 82–83

Минимальная планка (each choice / 1-wise): каждое значение каждого параметра встречается хотя бы в одном тесте; сам по себе 1-wise годится лишь для экспресс-проверки при жёстком дефиците времени.

**Как проверить:** Скриптом по таблице комбинаций и объявленной модели параметров (PICT-модель, таблица параметров в плане): для каждого параметра множество значений в наборе тестов равно множеству объявленных значений. Пропущенное значение — fail. Если параметры заданы только текстом требований, их сначала выписывает агент. Если весь набор построен как 1-wise не для экспресс-проверки — предупреждение.

### SRK-TD-030 · Сложные условия из требований оформляются таблицей решений

`should` · проверка: эвристика агента · для: requirements, test-plan · источник: `s1-c09-05`, с. 85–87

Если в требованиях много условий, связанных через «если / и / или / кроме / но если», а условий 2–5 с бинарными значениями, строят таблицу решений: условия — строки, действия — выходы, каждый столбец — тест.

**Как проверить:** Пре-фильтр по требованию: маркеры ветвления `(?i)\b(если|иначе|в\s+случае|за\s+исключением|кроме|при\s+условии|только\s+если|if|else|otherwise|unless|except)\b` (одиночные «и/или» без «если» не считать — они есть почти в любом тексте). Если фрагмент задаёт результат через ≥2 независимых бинарных условия, проверить, что в плане есть таблица решений или набор сценариев на каждую значимую комбинацию. Типовые места: сложные скидки и промокоды, роль × статус, взаимозависимые поля форм, статусы обработки заказа.

### SRK-TD-031 · Таблица решений полна: все 2^n комбинаций покрыты или явно исключены

`must` · проверка: эвристика агента · для: test-plan, test-cases · источник: `s1-c09-05`, с. 86–87

Для n бинарных условий существует 2^n правил; каждое должно либо иметь тест, либо быть явно помечено как невозможное или объединённое с другими (условие не влияет).

**Как проверить:** Агентом выделить n бинарных условий правила; перечислить 2^n комбинаций и сопоставить со сценариями плана (если в плане есть явная таблица решений, сверка столбцов выполняется механически). Комбинация без теста и без пометки «невозможно» / «объединено: условие не влияет» — fail.

### SRK-TD-039 · Для сущностей с жизненным циклом построена модель состояний и переходов

`must` · проверка: эвристика агента · для: requirements, test-plan, test-cases, test-code · источник: `s1-c09-07`, с. 90–91

Если поведение зависит от предыдущих действий (заказ, бронь, ячейка постамата, сброс пароля), выделяют состояния, события, переходы и действия-выходы и покрывают каждый допустимый переход с проверкой его выхода.

**Как проверить:** Найти в требованиях статусы сущности; восстановить диаграмму (состояние → событие → новое состояние → действие). Каждый переход без сценария в плане — fail; сценарий без проверки выходного действия (письмо, запись в БД) — предупреждение.

### SRK-TD-040 · Проверяются недопустимые события в каждом состоянии

`must` · проверка: эвристика агента · для: test-plan, test-cases, test-code, live-product · источник: `s1-c09-07`, с. 90–91

Тестируют попытки выполнить действие, недоступное в текущем состоянии: забрать посылку без ввода кода, заселиться по неоплаченной брони.

**Как проверить:** Для каждого состояния модели взять события, не ведущие из него по спецификации; в плане должны быть сценарии на хотя бы ключевые из них с ожиданием отказа без смены состояния.

## Рекомендации (10)

### SRK-TD-008 · Каждый стык классов проверяется по трём точкам (3BVA), а не по двум

`should` · проверка: эвристика агента · для: test-plan, test-cases, test-code · источник: `s1-c09-03`, с. 73–74

Использовать 3BVA: на каждом стыке классов брать саму граничную точку и по ближайшему соседу с каждой стороны (3 значения на стык). Пример книги: для правила «скидка от 10 товаров» — 9, 10, 11. Двухточечный вариант (граница и один сосед) автор считает устаревшим и допустимым лишь при аварийной нехватке времени.

**Почему:** По разбору автора третья точка ловит ошибки операторов сравнения, которые 2BVA пропускает: условие «= 10» вместо «>= 10» проходит проверки 9 и 10 и проявляется только на 11.

**Как проверить:** Агентом выписать стыки классов (L — последнее значение нижнего класса, F — первое значение верхнего, шаг = точность величины), затем механически сверить с тестовыми данными. Pass, если для стыка есть три подряд идущих значения, включающих L и F: {L−шаг, L, F} или {L, F, F+шаг}. Есть только L и F — это 2BVA, finding. Для порога вида «от N» (>= N) требовать именно N−шаг, N, N+шаг: без N+шаг не ловится ошибка «= N».

### SRK-TD-020 · План покрывает неявные требования, о которых умолчал аналитик

`should` · проверка: эвристика агента · для: test-plan, test-cases, requirements · источник: `s1-c09-03`, с. 74

Помимо явно описанных ограничений, сеньор-уровень покрытия включает общепринятые практики: количество файлов, имена, кодировки, спецсимволы, — даже если в ТЗ их нет.

**Как проверить:** Сравнить план с требованиями: если план покрывает только явно перечисленные ограничения (например, только размер и формат), а очевидные неявные аспекты (количество, имена, кодировка) не рассмотрены — флаг.

### SRK-TD-023 · Для нескольких независимых параметров применять pairwise

`should` · проверка: эвристика агента · для: test-plan, test-cases, test-code · источник: `s1-c09-04`, с. 80–85

Когда у функции несколько независимых параметров или фильтров, набор тестов строят попарным покрытием вместо полного перебора или случайной выборки.

**Как проверить:** Если у фичи ≥3 независимых параметров с ≥2 значениями (фильтры, калькуляторы, чекаут «оплата × доставка», экспорт «формат × кодировка × разделитель»), в плане должен быть комбинаторный набор с указанной стратегией. Ни полного перебора, ни обоснованного набора — флаг.

### SRK-TD-026 · Сила комбинаторного покрытия соответствует критичности домена

`should` · проверка: эвристика агента · для: test-plan · источник: `s1-c09-04`, с. 79–80

Полный перебор оправдан только для систем, где ошибка стоит жизней (атомная энергетика, космос, военные и медицинские системы); 3-wise — для критичных модулей финтеха и медицины; pairwise — стандарт для обычных продуктов.

**Как проверить:** Определить домен и критичность модуля: флаг, если транзакции/балансы финтеха покрыты слабее pairwise или для обычного веб-фильтра планируется полный перебор без обоснования.

### SRK-TD-032 · Из таблицы решений удаляют невозможные состояния и объединяют безразличные

`should` · проверка: эвристика агента · для: test-plan, test-cases · источник: `s1-c09-05`, с. 87

Комбинации, логически невозможные (сумма > 200, но не > 100), вычёркивают; правила, где часть условий не влияет на результат (незарегистрированный клиент отклоняется при любой сумме), сворачивают в один тест.

**Как проверить:** Проверить, что план не содержит тестов на невозможные комбинации и не дублирует сценарии, отличающиеся лишь условиями, которые не влияют на результат.

### SRK-TD-033 · Бизнес-правило определяет результат для каждой комбинации условий

`should` · проверка: эвристика агента · для: requirements · источник: `s1-c09-05`, с. 86–87

Требование с составными условиями должно задавать действие системы для всех комбинаций (включая ветку «иначе»); непокрытая комбинация — дыра в требованиях.

**Как проверить:** Построить таблицу решений по требованию; если для какой-то возможной комбинации результат не определён, зафиксировать находку и вопрос к аналитику.

### SRK-TD-037 · Для критичных систем строить граф причин и следствий с ограничениями

`nice` · проверка: эвристика агента · для: requirements, test-plan · источник: `s1-c09-06`, с. 88–90

В безопасностно-критичных доменах (медицина, авиация, автомобильные системы, космос) условия моделируют графом с логическими связками И/ИЛИ/НЕ и ограничениями E/I/O/R, а затем выводят из него таблицу решений без невозможных и дублирующих тестов.

**Как проверить:** Для safety-critical модулей проверить наличие модели причин-следствий или эквивалентного формального анализа условий; для обычных продуктов не требовать.

### SRK-TD-038 · Ограничения между условиями выявлены и учтены в наборе тестов

`should` · проверка: эвристика агента · для: requirements, test-plan · источник: `s1-c09-06`, с. 89

Взаимоисключение, «хотя бы одно», «ровно одно» и «требует» между условиями фиксируют явно: невозможные сочетания не тестируются как валидные, а само ограничение проверяется.

**Как проверить:** Выписать из требований зависимости условий (E/I/O/R). Флаг, если план содержит тест на комбинацию, нарушающую ограничение, как на допустимую, или нет проверки, что ограничение соблюдается (например, выбор самовывоза блокирует поле адреса).

### SRK-TD-046 · Error guessing дополняет формальные техники, а не заменяет их

`should` · проверка: эвристика агента · для: test-plan · источник: `s1-c09-08`, с. 94

Сначала строят каркас из классов эквивалентности, граничных значений и таблиц решений, затем добавляют сценарии по опыту; план только на интуиции пропускает базовые бизнес-сценарии.

**Как проверить:** Флаг, если план состоит в основном из «что может пойти не так» без систематического покрытия требований (EP/BVA/таблиц решений), или наоборот не содержит ни одного сценария error guessing для рискованных мест.

### SRK-TD-047 · Использовать историю дефектов команды как источник сценариев

`nice` · проверка: эвристика агента · для: test-plan · источник: `s1-c09-08`, с. 92–93

Идеи для проверок берут из прошлого опыта и накопленной таксономии багов команды на данном стеке (сбои при обрыве сети, отвалы авторизации, уязвимости БД).

**Как проверить:** Если в проекте есть история багов/постмортемы, проверить, что рецидивоопасные классы дефектов отражены в плане новой фичи схожего типа.

## Практические советы (4)

### SRK-TD-021 · У категориальных параметров нет границ — для них только классы

`nice` · проверка: эвристика агента · для: test-plan, test-cases · источник: `s1-c09-03`, с. 74

К неупорядоченным значениям (форматы файлов, варианты выбора) применяют классы эквивалентности, а не анализ границ.

**Как проверить:** Флаг, если план называет «граничными» проверки для перечислимых/категориальных параметров — это либо ошибка дизайна, либо пропущенные реальные границы.

### SRK-TD-028 · Сравнивать генераторы pairwise по размеру набора

`nice` · проверка: вручную · для: test-plan, test-cases · источник: `s1-c09-04`, с. 82

Разные генераторы дают наборы разного размера (в примере автора PICT выдаёт 9 строк при оптимуме 8), поэтому полезно сверить результат с альтернативным инструментом.

**Как проверить:** При большом наборе pairwise сравнить число строк от двух генераторов и взять меньший полный набор.

### SRK-TD-029 · Pairwise для совместимости браузеров/ОС применять с осторожностью

`nice` · проверка: эвристика агента · для: test-plan · источник: `s1-c09-04`, с. 84–85

### SRK-TD-062 · Подмена расширения и огромный файл при загрузке

`must` · проверка: эвристика агента · для: test-plan, test-cases, test-code, live-product · источник: `s1-c09-08`, с. 94

Загружают исполняемый файл, переименованный в изображение, и картинку очень большого размера (сотни мегабайт).

**Как проверить:** Есть сценарии: .exe, переименованный в .jpg (ожидается отказ по проверке содержимого, а не только расширения), и файл порядка 500 Мб (ожидается отказ по размеру с понятным сообщением, без падения клиента или сервера).
