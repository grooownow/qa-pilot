## Жёсткие правила (11)

### SRK-API-001 · Сайт и API работают только по HTTPS

`must` · проверка: детерминированно · для: live-product, test-plan, test-code · источник: `s2-c01-03`, с. 113–114 · авторитет: industry-practice · сверка со стандартом: aligned

Все страницы и API-эндпоинты должны отдаваться по HTTPS; обращение по HTTP должно перенаправлять на HTTPS, а не обслуживать трафик в открытом виде.

**Почему:** По HTTP запрос, куки, пароли и содержимое ответа видны любому в сети и провайдеру.

**Как проверить:** Для базового URL и ключевых эндпоинтов: запрос по http:// должен вернуть 301/308 с Location на https://; все запросы в DevTools Network идут по https. Fail — страница/API отвечает 200 по http:// или есть mixed content.

**Сегодня:** Для API OWASP рекомендует отдавать только HTTPS-эндпоинты; отказ на http:// (без редиректа) допустим и даже предпочтителен, т.к. редирект не защищает уже отправленные в открытом виде токены. Для сайтов — редирект + HSTS.

### SRK-API-005 · GET безопасен: не меняет состояние на сервере

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-04`, с. 115 · авторитет: normative · сверка со стандартом: aligned

GET-запрос должен только читать данные: вызов GET не должен создавать, изменять или удалять сущности.

**Как проверить:** В API-тесте: снять состояние ресурса (или счётчик/БД), выполнить GET несколько раз, повторно снять состояние — assert равенства. Fail — после GET изменились данные.

**Сегодня:** По RFC 9110 §9.2.1 safe-метод может иметь побочные эффекты на сервере (логи, счётчики просмотров, аналитика), если клиент их не запрашивал; проверять нужно бизнес-состояние, а не любые счётчики.

### SRK-API-006 · PUT идемпотентен: повтор даёт тот же результат

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-04`, с. 116–117 · авторитет: normative · сверка со стандартом: aligned

Повторная отправка одного и того же PUT на ресурс должна оставлять ресурс в одинаковом состоянии и не создавать новых записей.

**Как проверить:** API-тест: отправить идентичный PUT /resource/{id} 2+ раза, затем GET — assert, что тело совпадает с отправленным и число записей в коллекции не изменилось.

### SRK-API-014 · Ошибка валидации не возвращается как 200 OK

`must` · проверка: детерминированно · для: test-code, live-product, test-plan · источник: `s2-c01-05`, с. 119–120 · авторитет: normative · сверка со стандартом: aligned

Если запрос не прошёл валидацию, API должно ответить кодом 4xx, а не 200 с текстом ошибки в теле. Ответ 200 при ошибке — дефект реализации API.

**Как проверить:** Негативный API-тест с невалидными данными: assert response.status в диапазоне 400–499. Fail — status 200 при наличии в теле признаков ошибки ("error", "status":"error").

### SRK-API-015 · Сбой сервера отдаёт 5xx, а не 200 с ошибкой в JSON

`should` · проверка: детерминированно · для: live-product, test-code · источник: `s2-c01-05`, с. 122–123 · авторитет: normative · сверка со стандартом: aligned

Падение бэкенда или БД должно отражаться статусом 5xx. Ответ 200 OK с {"status":"error"} внутри — антипаттерн «псевдо-REST»; QA обязан подсветить этот риск команде.

**Почему:** Такие ответы обманывают автотесты, мониторинг и аналитику.

**Как проверить:** В DevTools Network/логах API-тестов искать ответы со статусом 200, в теле которых есть поля ошибки (status: error, code: 5xx, message об исключении). Любое совпадение — finding.

### SRK-API-059 · Ломающее изменение API — только с новой мажорной версией

`must` · проверка: детерминированно · для: requirements, test-code · источник: `s2-c02-06`, с. 144 · авторитет: industry-practice · сверка со стандартом: aligned

Удаление или переименование поля, смена структуры — breaking change, требующий новой мажорной версии (v1 → v2). Добавление необязательного поля версию не меняет.

**Почему:** Иначе падают старые версии мобильных приложений у пользователей.

**Как проверить:** Сравнить OpenAPI/схему текущей и предыдущей версии (oasdiff, openapi-diff): при обнаружении breaking changes в той же мажорной версии — fail.

### SRK-API-073 · Бэкенд-валидацию тестировать напрямую через API, в обход UI

`must` · проверка: эвристика агента · для: test-plan, test-code · источник: `s2-c05-00`, с. 174–175 · авторитет: industry-practice · сверка со стандартом: aligned

Проверки формы в браузере не защищают сервер: злоумышленник или интеграция шлют запросы напрямую. План должен содержать негативные API-тесты для всех полей тела запроса, включая служебные ключи, которых нет на форме.

**Почему:** Тестирование фронтенда не равно тестированию бэкенда; каждая пара ключ-значение в запросе — отдельная точка отказа.

**Как проверить:** Сравнить поля тела запроса (из Network/OpenAPI) с негативными сценариями плана/тестов. Fail — негатив проверен только через UI или служебные поля (id, флаги, даты) не покрыты API-тестами.

### SRK-API-088 · POISED-S: ни один эндпоинт с данными не доступен без авторизации

`must` · проверка: детерминированно · для: test-code, test-plan, live-product · источник: `s2-c05-03`, с. 181 · авторитет: industry-practice · сверка со стандартом: aligned

Проверь каждый защищённый эндпоинт, включая списки, без токена/cookie и с испорченным или просроченным токеном: все должны отвечать 401 и не отдавать данные. Частая дыра — защищён детальный GET /items/:id, но забыт список GET /items с чужими персональными данными.

**Как проверить:** Пройти по всем эндпоинтам из OpenAPI/коллекции без Authorization и Cookie, а также с испорченным токеном — assert 401 и отсутствие данных в теле для всех, кроме явно публичных. Любой 200 с персональными данными — критический дефект.

### SRK-API-089 · POISED-S: сервер не доверяет клиенту флаги оплаты и привилегий

`must` · проверка: детерминированно · для: test-code, test-plan, requirements · источник: `s2-c05-03`, с. 181–182 · авторитет: industry-practice · сверка со стандартом: aligned

Поля, отражающие оплату, роль или статус (depositpaid: true, is_admin), не должны приниматься от клиента на веру: подставь их в тело запроса и убедись, что сервер их игнорирует или отклоняет.

**Почему:** В примере клиент передал признак оплаченного залога, и бэкенд принял бронь как оплаченную без эквайринга.

**Как проверить:** API-тест: создать/обновить сущность с привилегированными полями (paid=true, role=admin, status=approved) — assert, что в сохранённой сущности (через GET) значения выставлены сервером, а не клиентом.

### SRK-API-123 · Сбой запроса: не вечный спиннер, а экран ошибки с повтором

`must` · проверка: детерминированно · для: live-product, test-plan, test-code · источник: `s2-c10-04`, с. 228–229 · авторитет: industry-practice · сверка со стандартом: aligned

При недоступности эндпоинта интерфейс должен убрать индикатор загрузки и показать понятное сообщение с возможностью обновить, а не зависнуть с бесконечным лоадером.

**Как проверить:** Заблокировать запрос (DevTools Block request URL или page.route → abort()): assert в разумный срок исчезает лоадер и виден текст ошибки и кнопка повтора.

### SRK-API-128 · Пользователь не может менять и удалять чужие данные через API

`must` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c11-06`, с. 241 · авторитет: industry-practice · сверка со стандартом: aligned

Через прямой API-запрос проверь, что пользователь не может изменить или удалить чужой ресурс (комментарий, бронь), подставив его идентификатор, даже если в интерфейсе такой кнопки нет.

**Почему:** Фронтенд легко обойти, реальную безопасность показывает только прямое тестирование API.

**Как проверить:** API-тест: под пользователем A выполнить PUT/PATCH/DELETE на ресурс пользователя B — assert 403 (или 404) и неизменность ресурса через GET от B.

## Рекомендации (53)

### SRK-API-002 · Content-Type запроса и ответа соответствует формату тела

`should` · проверка: детерминированно · для: test-code, live-product · источник: `s2-c01-03`, с. 112–113 · авторитет: normative · сверка со стандартом: aligned

Запросы с телом должны передавать заголовок Content-Type, совпадающий с фактическим форматом (например application/json), а ответ — Content-Type, соответствующий тому, что реально лежит в теле.

**Как проверить:** В API-тестах: assert, что response.headers['content-type'] начинается с ожидаемого типа (application/json) и тело парсится этим форматом; в запросах с body явно задан Content-Type. Fail — JSON отдается как text/html или заголовок отсутствует.

### SRK-API-003 · Повтор неидемпотентного действия (POST, «списать») — проверить на дубли

`should` · проверка: эвристика агента · для: test-plan, test-code, live-product · источник: `s2-c01-04`, с. 114–115

POST и другие действия «с приращением» (списать сумму, добавить запись) не идемпотентны: каждый повтор меняет состояние заново. План и тесты должны покрывать повторную отправку (двойной клик, повтор сети) и проверять, сколько раз эффект применился и допустимо ли это по требованиям.

**Почему:** Повтор POST создаёт дубли с новыми ID, а пятикратное «списать 100 ₽» спишет 500 ₽.

**Как проверить:** В тест-плане/тестах на создание ресурса и денежные/счётные операции найти сценарий двойной отправки или быстрого многократного клика с проверкой итогового состояния (число записей, баланс). Fail — сценария нет. На живом продукте: дважды быстро нажать «Создать/Оплатить» и посмотреть в списке/Network, сколько раз применилось действие.

### SRK-API-007 · PUT с неполным телом: поля затираются или 4xx

`should` · проверка: эвристика агента · для: test-plan, test-code · источник: `s2-c01-04`, с. 116

PUT требует полного представления объекта. Покрыть сценарий PUT без части полей (включая серверные, например created_at) и зафиксировать поведение: ошибка валидации или затирание полей — должно соответствовать спецификации.

**Как проверить:** В плане/тестах для PUT-эндпоинта искать негативный сценарий с неполным телом и проверку итогового состояния через GET. Fail — сценария нет или он не проверяет, какие поля остались.

### SRK-API-008 · PUT на коллекцию без ID возвращает ошибку

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-04`, с. 116 · авторитет: industry-practice · сверка со стандартом: aligned

PUT адресуется конкретному ресурсу; запрос PUT на коллекцию без идентификатора должен завершаться ошибкой, а не создавать/перезаписывать данные.

**Как проверить:** API-тест: PUT /collection (без {id}) — assert статус 4xx (обычно 405 или 404) и отсутствие изменений в коллекции.

**Сегодня:** RFC 9110 §9.3.4 не запрещает PUT на URI коллекции (замена её состояния); ожидать 405/404 стоит, только если контракт этот метод не заявляет.

### SRK-API-009 · PATCH меняет только переданные поля

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-04`, с. 117 · авторитет: normative · сверка со стандартом: aligned

После PATCH с частью полей проверить, что изменились только они, а остальные поля ресурса сохранили прежние значения.

**Как проверить:** API-тест: GET до, PATCH с одним полем, GET после — assert, что изменилось только переданное поле, остальные равны значениям до запроса.

### SRK-API-010 · Повторный DELETE не ломает состояние

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-04`, с. 117 · авторитет: normative · сверка со стандартом: aligned

DELETE идемпотентен: повторное удаление уже удалённого ресурса должно вернуть 404 или 204 без побочных изменений в данных, а не 5xx.

**Как проверить:** API-тест: DELETE /resource/{id} дважды — первый 200/204, второй assert статус in (404, 204); последующий GET возвращает 404. Fail — 500 или изменение других данных.

### SRK-API-011 · Не передавать чувствительные данные и большие фильтры в query-строке

`should` · проверка: эвристика агента · для: live-product, requirements, test-code · источник: `s2-c01-04`, с. 117–118

Конфиденциальные параметры не должны уходить в URL GET-запроса — они оседают в логах. Для длинных наборов фильтров проверить, что URL не упирается в лимит длины (414), и рассмотреть передачу условий в теле.

**Почему:** Десятки фильтров в URL приводят к 414 URI Too Long и светят данные в логах.

**Как проверить:** В Network просмотреть URL запросов: ищите токены, пароли, email, персональные данные в query-параметрах (регэкспом по token|password|email|phone). Для поиска с фильтрами: выставить максимум фильтров и проверить, что запрос не падает с 414.

**Сегодня:** Метод QUERY, который автор подаёт как тренд, на момент 2026 года всё ещё черновик IETF (HTTP QUERY method), а не утверждённый RFC; поддержка серверами, прокси и клиентскими библиотеками неполная — проверяйте её перед использованием.

### SRK-API-016 · API-тест проверяет HTTP статус-код, а не только тело

`should` · проверка: детерминированно · для: test-code, live-product · источник: `s2-c01-05`, с. 123 · авторитет: industry-practice · сверка со стандартом: aligned

Проверяя ответ (в DevTools или в API-тесте), смотри не только тело, но и фактический HTTP-статус; в автотестах статус должен утверждаться явно.

**Как проверить:** Grep по API-тестам: в каждом тесте есть assert статуса (expect(res.status()).toBe(..), toBeOK(), status_code ==). Fail — тест проверяет только поля тела. На живом продукте: в Network сверить статус каждого ключевого запроса, а не только содержимое Response.

### SRK-API-018 · Создание ресурса возвращает 201 Created

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-05`, с. 120 · авторитет: normative · сверка со стандартом: aligned

Успешное создание ресурса (POST или создающий PUT) по REST-контракту должно отвечать 201 Created; если контракт обещает вернуть созданную сущность, в ней должны быть серверные поля (например id).

**Как проверить:** API-тест на создание: assert status == 201; если спецификация описывает тело ответа — assert наличие id/серверных полей. Fail — 200/204 без явного решения в контракте или иной код.

### SRK-API-019 · 204 No Content — без тела ответа

`nice` · проверка: детерминированно · для: test-code · источник: `s2-c01-05`, с. 120 · авторитет: normative · сверка со стандартом: aligned

Ответ 204 (типичный для DELETE) не должен содержать тела; клиент должен корректно обрабатывать пустой ответ.

**Как проверить:** API-тест: при status == 204 assert пустое тело (длина 0).

### SRK-API-020 · Асинхронные операции: 202 и опрос до готовности

`should` · проверка: эвристика агента · для: test-plan, test-code, live-product · источник: `s2-c01-05`, с. 120

Для долгих операций (генерация отчёта) API может отвечать 202 Accepted, а клиент — опрашивать статус до 200. План должен покрывать промежуточное состояние, успешное завершение и зависший/упавший процесс.

**Как проверить:** Для фич с фоновой обработкой проверить в плане сценарии: ответ 202, корректный индикатор ожидания в UI, переход к результату после 200, поведение при ошибке/таймауте опроса.

### SRK-API-022 · Недостаточно прав у роли → 403

`must` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-05`, с. 121 · авторитет: normative · сверка со стандартом: aligned

Аутентифицированный пользователь без прав на действие (обычный юзер удаляет админа) должен получать 403 Forbidden, а действие не должно выполняться.

**Как проверить:** API-тест под низкоправной ролью на привилегированное действие: assert status == 403 и проверить через GET, что ресурс не изменён. Fail — 200/204 или 404 вместо 403 без явного решения в спеке.

### SRK-API-023 · Несуществующий ресурс → 404

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-05`, с. 121 · авторитет: normative · сверка со стандартом: aligned

Запрос к несуществующему ID или URL должен возвращать 404 Not Found, а не 200 с пустым телом или 500.

**Как проверить:** API-тест: GET/PUT/DELETE по заведомо несуществующему id — assert status == 404.

### SRK-API-024 · Неподдерживаемый метод → 405

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-05`, с. 121 · авторитет: normative · сверка со стандартом: aligned

Вызов эндпоинта методом, который он не поддерживает (например, POST на /cats/123), должен давать 405 Method Not Allowed.

**Как проверить:** API-тест: отправить на эндпоинт методы, не указанные в спеке — assert status == 405 (желательно с заголовком Allow).

**Сегодня:** RFC 9110 §15.5.6: при 405 заголовок Allow обязателен (MUST), а не «желателен».

### SRK-API-025 · Конфликт состояния → 409 (дубликат, гонка за последний товар)

`should` · проверка: детерминированно · для: test-plan, test-code · источник: `s2-c01-05`, с. 121 · авторитет: normative · сверка со стандартом: aligned

Покрыть сценарии конфликта: регистрация на уже занятый email, одновременная покупка последней единицы товара двумя пользователями. Ожидается 409 Conflict и целостные данные.

**Как проверить:** API-тест: повторно создать сущность с уникальным полем — assert 409; параллельно отправить две покупки последнего товара — ровно одна успешна, вторая 409, остаток не уходит в минус.

**Сегодня:** 409 на занятый email раскрывает существование аккаунта; OWASP Authentication Cheat Sheet рекомендует при регистрации нейтральный ответ без перечисления пользователей.

### SRK-API-026 · Битый JSON → 400 Bad Request

`should` · проверка: детерминированно · для: test-code, test-plan · источник: `s2-c01-05`, с. 121 · авторитет: normative · сверка со стандартом: aligned

### SRK-API-013 · HEAD отдаёт только заголовки, без тела

`nice` · проверка: детерминированно · для: test-code · источник: `s2-c01-04`, с. 119 · авторитет: normative · сверка со стандартом: aligned

HEAD должен возвращать те же заголовки, что и GET, но без тела; это удобно, чтобы узнать размер файла по Content-Length без скачивания.

**Как проверить:** Отправить HEAD и GET на один ресурс: assert пустое тело у HEAD и совпадение Content-Type/Content-Length с GET.

**Сегодня:** RFC 9110 §9.3.2: сервер SHOULD отдавать те же заголовки, что и GET, но MAY опустить генерируемые при формировании тела (например, Content-Length).

**Как проверить:** В баг-репортах про ошибки данных/отображения проверить наличие запроса, статус-кода и тела ответа и корректного компонента (frontend/backend). Fail — нет сведений о сетевом ответе или слой указан вопреки статусу.

### SRK-API-032 · Редирект с POST должен сохранять метод (307/308)

`nice` · проверка: эвристика агента · для: live-product, test-code · источник: `s2-c01-05`, с. 121 · авторитет: normative · сверка со стандартом: conflict
