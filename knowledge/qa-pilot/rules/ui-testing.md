# ui-testing

Сгенерировано из `ui-testing.json` скриптом `scripts/kb/render_rules.py` — правьте JSON, не этот файл.
Собственные правила qa-pilot: источник каждого правила указан в поле «источник».

## Жёсткие правила (7)

### QAP-UI-001 · У атома есть история на каждое состояние

`must` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Interaction tests (https://storybook.js.org/docs/writing-tests/interaction-testing), пересказ; Storybook docs, Accessibility tests (https://storybook.js.org/docs/writing-tests/accessibility-testing), пересказ · авторитет: industry-practice · сверка со стандартом: aligned

Каждый атом библиотеки компонентов (компонент, который не использует других компонентов этой библиотеки) имеет историю на каждое состояние: варианты, размеры, disabled, loading, error, empty, длинное содержимое, фокус. Состояние, которого нет в API компонента, не требуется.

**Почему:** История — это и документация, и входная точка для тестов и a11y-проверок. Состояние без истории не проверяется никем, и поломка вылезает только на странице продукта.

**Как проверить:** Для каждого атома сравнить пропсы и ветки рендера (variant, size, disabled, loading, error, empty) со списком историй. Находка: состояние есть в API, историй на него нет.

### QAP-UI-002 · У поведения атома есть интерактивный тест

`must` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Interaction tests (https://storybook.js.org/docs/writing-tests/interaction-testing), пересказ; Storybook docs, Vitest addon (https://storybook.js.org/docs/writing-tests/integrations/vitest-addon), пересказ; Testing Library, Guiding Principles (https://testing-library.com/docs/guiding-principles), пересказ · авторитет: industry-practice · сверка со стандартом: aligned

Каждое поведение атома проверено интерактивным тестом (play-функция в истории или эквивалент в принятом в проекте раннере): клик, клавиатура, открытие и закрытие, валидация, контролируемое и неконтролируемое значение. Локаторы в истории подчиняются жёсткому правилу test-id из references/e2e-patterns.md.

**Почему:** Атом используется десятками мест. Тест поведения на уровне атома ловит поломку один раз и сразу, а не в каждом экране, который его применяет.

**Как проверить:** Для каждого атома перечислить обработчики и управляемые значения (onClick, onChange, onKeyDown, open/close, validate, value/defaultValue). Находка: поведение есть, play-теста или компонентного теста на него нет.

### QAP-UI-003 · Тест композиции не перепроверяет поведение атомов

`must` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Interaction tests (https://storybook.js.org/docs/writing-tests/interaction-testing), пересказ; Testing Library, Guiding Principles (https://testing-library.com/docs/guiding-principles), пересказ · авторитет: industry-practice · сверка со стандартом: aligned

Тест композиции (компонента, собранного из атомов) проверяет только то, что добавляет сама композиция: связку атомов, состояние, которое передаётся между ними, собственную логику. Поведение вложенного атома (клик по кнопке, валидация поля) в тесте композиции не проверяется заново.

**Почему:** Повторная проверка атома в каждой композиции умножает тесты, ломает их все при одном изменении атома и создаёт видимость покрытия композиции. Поведение атома уже проверено на его уровне (QAP-UI-002).

**Как проверить:** В тестах композиции найти проверки, которые были бы теми же в тесте вложенного атома (состояния самого атома, его клавиатура, его валидация). Находка: такая проверка есть, а у композиции нет теста на её собственную связку.

### QAP-UI-004 · У состояния истории с поведением есть play-тест

`must` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Interaction tests (https://storybook.js.org/docs/writing-tests/interaction-testing), пересказ; Storybook docs, Vitest addon (https://storybook.js.org/docs/writing-tests/integrations/vitest-addon), пересказ · авторитет: industry-practice · сверка со стандартом: aligned

Если состояние, показанное историей, имеет поведение (раскрывается, переключается, показывает ошибку после ввода, реагирует на клавиши), то у этой истории есть play-функция, которая это поведение проверяет. История без play допустима только для состояний без поведения.

**Почему:** История без play-теста только рисуется: она зелёная, даже когда кнопка перестала срабатывать. Сборка историй создаёт впечатление покрытия, которого нет.

**Как проверить:** В файлах историй найти состояния с поведением (open, expanded, error, interactive) и проверить наличие play у истории или другого теста на него. Находка: поведение без play-теста.

### QAP-UI-005 · Сложный UI уровня приложения проверяется шагом e2e-флоу

`should` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Interaction tests (https://storybook.js.org/docs/writing-tests/interaction-testing), пересказ — границы компонентных тестов; qa-pilot: стратегия снизу вверх (references/ui-testing.md) · авторитет: industry-practice · сверка со стандартом: aligned

Поведение, которому нужно настоящее приложение (маршрутизация, данные, авторизация), проверяется шагом внутри e2e-флоу, а не отдельным UI-тестом с набором моков. Компонентный тест с моками роутера и данных не заменяет этот шаг.

**Почему:** Компонентный тест с замоканным окружением проверяет моки. Реальная связка экрана с маршрутом и данными ломается там, где моков нет.

**Как проверить:** Найти компонентные тесты и истории, где мокаются маршрутизация или загрузка данных ради проверки поведения всего экрана. Находка: для этого экрана нет шага в e2e-флоу.

### QAP-UI-006 · Визуальные снимки только для стабильных компонентов и закреплённого окружения

`should` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Vitest addon (https://storybook.js.org/docs/writing-tests/integrations/vitest-addon), пересказ; qa-pilot: QAP-TC-024 · авторитет: industry-practice · сверка со стандартом: aligned

Визуальные снимки делаются только для стабильных детерминированных компонентов и только там, где CI рендерит в закреплённом окружении (тот же образ ОС, браузер, шрифты). Снимок никогда не единственная проверка поведения (QAP-TC-024).

**Почему:** В незакреплённом окружении снимки расходятся из-за шрифтов и субпикселей, и команду приучают принимать диффы без чтения. Снимок показывает, что изменилось, но не что сломалось.

**Как проверить:** Найти тесты снимков (toHaveScreenshot, toMatchSnapshot по картинке, visual-тесты). Находка: компонент с анимацией, случайными или датированными данными; CI на неопределённом образе; снимок как единственный expect в тесте поведения.

### QAP-UI-007 · UI-тесты запускаются в CI или отмечены как локальные

`should` · проверка: эвристика агента · для: test-code, test-plan · источник: Storybook docs, Interaction tests (https://storybook.js.org/docs/writing-tests/interaction-testing), пересказ; Storybook docs, Vitest addon (https://storybook.js.org/docs/writing-tests/integrations/vitest-addon), пересказ · авторитет: industry-practice · сверка со стандартом: aligned

Раннер UI-тестов (Storybook test-runner, Vitest addon, компонентные тесты Playwright) запускается в CI. Если нет, отчёт сообщает, что эти тесты считаются только локальными, и не называет их покрытием.

**Почему:** Тесты, которые никто не запускает автоматически, устаревают молча: истории ломаются, а зелёного сигнала нет и красного тоже.

**Как проверить:** Найти команду раннера UI-тестов в package.json и проверить, что workflow CI вызывает её. Находка: раннер есть, а в CI его нет.
